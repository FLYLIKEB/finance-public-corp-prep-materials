# 10-01. 암호화와 해시

> 학습 목적: 암호화와 해시의 목적 차이를 구분한다.
> 관련 기출: [05-12-보안-기출-모음](05-12-보안-기출-모음.md)
> 연결 핵심정리: [04-4-네트워크-프로토콜-보안](04-04-네트워크-프로토콜-보안.md)

## 핵심 개념

- 암호화는 복호화를 전제로 데이터를 보호한다. 즉, 적절한 키(또는 키 쌍)를 가진 주체는 원문을 복원할 수 있다. 기밀성(confidentiality)을 주된 목표로 삼는다.
- 해시는 일방향 요약값을 만든다. 원문으로 복원하기 어렵고 주로 무결성(integrity) 확인이나 데이터 식별에 사용된다.
- 대칭키와 공개키 방식의 키 사용 차이를 암기한다. 대칭키는 같은 키로 암복호화(빠름, 키 분배 문제), 공개키는 공개/비밀키 쌍(키 분배와 인증에 유리, 연산 비용 큼).

### 서술형 확장 개념

- 정보보호의 기본 목표는 **기밀성(Confidentiality), 무결성(Integrity), 가용성(Availability) — CIA**이다. 추가로 인증(Authentication), 인가(Authorization), 감사(Accounting/Audit)를 함께 고려한다.
- 암호화 방식
  - 대칭키 암호: AES 계열 등. 빠르고 대량 데이터 암호화에 적합하지만 키를 안전하게 배포·보관해야 함.
  - 공개키 암호: RSA, ECC 등. 키 배포(공개키는 자유롭게 배포)와 전자서명에 유리하나 연산 비용이 높음.
  - 실무에서는 TLS처럼 공개키를 사용해 세션의 대칭키(세션키)를 안전하게 교환한 뒤, 데이터를 대칭키로 암호화하는 하이브리드 방식을 사용해 성능과 보안을 모두 만족시킨다.
- 무결성 및 인증
  - 전자서명: 개인키로 서명, 공개키로 검증. 무결성 확인, 서명 주체 인증, 부인방지(non-repudiation)에 유리.
  - MAC/HMAC: 공유 비밀키로 생성하는 무결성/인증 태그. 빠르지만 제3자에게 부인방지를 증명하기 어렵다(제3자는 같은 키로 태그를 생성할 수 있기 때문).
- 해시 속성
  - preimage resistance: 해시값으로부터 원문을 찾기 어려워야 함.
  - second preimage resistance: 주어진 메시지와 같은 해시를 갖는 다른 메시지를 찾기 어려워야 함.
  - collision resistance: 서로 다른 두 메시지가 같은 해시값을 갖도록 하는 쌍을 찾기 어려워야 함.
- 비밀번호 저장
  - 단순 해시는 취약하다. 반드시 고유한 salt(사용자별 고유값)를 사용하고 반복 계산(stretching, KDF)을 적용해 무차별 대입 공격과 레인보우 테이블 공격의 비용을 높여야 한다. 실무적으로는 bcrypt, scrypt, Argon2, PBKDF2 같은 검증된 KDF를 사용한다.

| 기술 | 제공 속성 | 핵심 차이 |
| --- | --- | --- |
| 암호화 | 기밀성 | 복호화 가능 |
| 해시 | 무결성 확인 | 일방향 요약 |
| HMAC | 무결성+인증 | 공유키 필요 |
| 전자서명 | 무결성+인증+부인방지 | 개인키 서명/공개키 검증 |

## 쉽게 이해하기

- 암호화는 자물쇠가 있는 상자에 내용을 넣는 것이다. 열쇠가 있으면 다시 원문을 볼 수 있다.
- 해시는 내용물을 고정 길이 지문으로 바꾸는 것이다. 지문으로 원문을 되돌리기는 어렵고, 지문이 다르면 내용이 다르다는 것을 빠르게 확인할 수 있다.
- 비밀번호 저장에는 복호화가 필요 없는 해시 기반 기법(KDF+salt)이 적합하고, 메시지 기밀성(예: 클라이언트-서버 통신)에는 암호화가 필요하다.

## 시험 포인트 (빈출/기억해야 할 항목)

- 암호화 vs 해시의 목적과 차이점(기밀성 vs 무결성)
- 대칭키 vs 공개키: 각각의 장단점과 사용 사례(TLS의 하이브리드 구조 설명 가능)
- 전자서명과 MAC/HMAC의 차이: 인증과 부인방지의 차이점을 사례로 설명
- 해시의 3가지 안전성 속성(preimage, second-preimage, collision)을 정의하고 의미를 설명
- 비밀번호 저장 시 salt와 반복 계산의 필요성 및 대표적인 KDF 예시(bcrypt, Argon2, PBKDF2 등)를 말할 수 있어야 함
- SHA-1과 같은 취약 알고리즘의 교체 필요성(충돌 공격 등) — 최신 표준을 사용해야 함

## 실무 연결 (구현·운영 관점에서 꼭 챙겨야 할 것)

- 암호 선택
  - 대칭 암호는 AES(블록 암호), 스트림 암호 또는 AEAD(AES-GCM, ChaCha20-Poly1305) 사용 권장 — 기밀성과 무결성을 동시에 제공하는 AEAD를 선호.
  - 공개키는 RSA, ECC를 용도에 맞게 사용. 서명이나 키교환에 적합한 알고리즘과 키 길이를 정책으로 정하고 주기적으로 갱신(키 회전).
- 비밀번호 저장
  - 사용자별 salt + 검증된 KDF(Argon2, bcrypt, scrypt, PBKDF2) 사용. 단순 SHA 계열만으로는 안 됨.
  - salt는 고유해야 하고 DB에 같이 보관되지만 비밀번호는 평문 저장 금지.
- 서명과 인증
  - 전자서명은 소프트웨어 무결성 검증, 코드 서명, 증명서(공개키 기반구조 PKI)에서 사용.
  - HMAC은 API 요청의 무결성·인증에 적합하지만, 부인방지 요구가 있는 경우 전자서명 필요.
- 키 관리
  - 비밀키(특히 개인키)는 안전한 장소(HSM 또는 키 관리 시스템)에 보관하고 접근 제어·감사 로그를 적용.
  - 키 회전, 폐기 정책, 백업 정책을 마련.
- 구현 주의사항
  - '직접 만든 암호화(roll-your-own crypto)' 금지: 검증된 라이브러리와 표준 모드(AEAD, CBC+MAC이 아닌 AEAD 우선)를 사용.
  - IV/nonce는 중복되지 않게 사용(재사용 시 보안 문제 발생).

## 예시 명령어 (학습용, 환경에 따라 도구/옵션이 다를 수 있음)

```bash
# 문자열의 SHA-256 해시(리눅스 환경 예시)
echo -n "password123" | sha256sum

# HMAC-SHA256 예시 (OpenSSL 이용)
# -mac HMAC -macopt key:yourkey
echo -n "message" | openssl dgst -sha256 -mac HMAC -macopt hexkey:616263

# 파일 대칭 암호화(테스트용, 실제 서비스에서는 키/IV 관리 필요)
openssl enc -aes-256-cbc -salt -in plain.txt -out cipher.bin -pass pass:yourpassword
```

> 위 예시는 개념 이해용이며, 실제 서비스에선 안전한 키/IV 관리, 적절한 파라미터(예: KDF 비용 인자) 설정과 검증된 라이브러리 사용이 필요하다.
