# 14-1. CPU 설계

## 파이프라인

파이프라인은 명령어 실행 단계를 나누어 여러 명령어를 겹쳐 처리하는 방식입니다. 일반적으로 인출(IF), 해독(ID), 실행(EX), 메모리 접근(MEM), 기록(WB) 단계로 설명합니다. 처리량은 증가하지만 각 단계가 독립적으로 흘러가야 하므로 해저드 처리가 중요합니다.
![14-1. CPU 설계 SVG 인포그래픽](https://cs.chamung.com/public/wiki-assets/14-1-cpu-infographic.svg)
> 그림: 파이프라인, 해저드, 확장 설계를 한눈에 요약한 SVG 인포그래픽.
> 출처: 내부 생성 자산 (`https://cs.chamung.com/public/wiki-assets/14-1-cpu-infographic.svg`)

파이프라인 5단계를 짧게 정리하면 다음과 같습니다.

- IF: 명령어를 가져오고 프로그램 카운터를 갱신한다.
- ID: 명령어를 해독하고 필요한 레지스터 값을 읽는다.
- EX: 산술·논리 연산이나 주소 계산, 분기 조건 판단을 수행한다.
- MEM: load/store 명령이 메모리에 접근한다.
- WB: 최종 결과를 레지스터 파일에 기록한다.

면접형 문제에서는 "파이프라인은 지연시간보다 처리량을 높이기 위한 구조"라는 표현을 같이 적어 주면 안정적입니다.

![CPU 파이프라인 겹침 GIF](https://cs.chamung.com/public/wiki-assets/14-1-pipeline-overlap.gif)

같은 시점에 IF·ID·EX·MEM·WB가 서로 다른 명령어를 맡아 흘러가고, load-use 상황에서는 한 칸의 bubble이 끼어 처리량이 꺾이는 모습을 함께 보면 해저드 개념이 더 직관적입니다.

![14-1. CPU 파이프라인 흐름 SVG](https://cs.chamung.com/public/wiki-assets/14-1-pipeline-flow.svg)
> 그림: 한 명령어의 5단계 실행과 여러 명령어가 겹쳐 흐르는 파이프라인 처리량 개념을 분리해 보여주는 SVG.

## 해저드 종류

| 종류 | 의미 | 해결 방식 |
|---|---|---|
| 구조적 해저드 | 하드웨어 자원 충돌 | 자원 분리, 스톨 |
| 데이터 해저드 | 이전 명령 결과가 아직 준비되지 않음 | 포워딩, 스톨, 레지스터 리네이밍 |
| 제어 해저드 | 분기 결과를 알기 전 다음 명령을 가져옴 | 분기 예측, 파이프라인 플러시 |

- 구조적 해저드: 같은 사이클에 명령어 인출과 데이터 접근이 같은 메모리 포트를 요구하면 충돌이 난다.
- 데이터 해저드: 특히 RAW(Read After Write)가 자주 나오며, load-use 패턴은 포워딩만으로 해결되지 않아 버블이 필요할 수 있다.
- 제어 해저드: 분기 결과를 늦게 알수록 잘못 가져온 명령을 더 많이 폐기하므로 파이프라인이 깊을수록 손해가 커진다.

```text
add r1, r2, r3
sub r4, r1, r5   <- r1이 아직 준비되지 않았다면 데이터 해저드
```

## 슈퍼스칼라

슈퍼스칼라는 한 클럭에 여러 명령어를 동시에 발행하는 구조입니다. 명령어 수준 병렬성(ILP)을 활용하지만, 데이터 의존성과 분기 실패가 많으면 성능 향상이 제한됩니다.

- 발행 폭(issue width)이 넓을수록 이상적인 처리량은 증가한다.
- 다만 의존성 검사, 레지스터 리네이밍, 재정렬 버퍼 같은 추가 하드웨어가 필요해 설계 복잡도가 커진다.
- 금융권 배치 서버처럼 처리량이 중요한 환경에서는 유리하지만, 저지연 시스템에서는 branch miss와 cache miss가 체감 성능을 더 크게 흔들 수 있다.

## 분기 예측

분기 예측은 조건 분기의 결과를 미리 추정해 파이프라인을 멈추지 않도록 합니다. 예측 실패 시 이미 가져온 명령을 버리는 플러시 비용이 발생합니다. 금융권 대용량 처리 시스템에서는 CPU 자체보다 I/O 병목이 큰 경우가 많지만, 저지연 거래 시스템에서는 분기 예측과 캐시 적중률도 성능에 영향을 줍니다.

- 정적 예측은 간단하지만 적응력이 낮고, 동적 예측은 실행 이력을 사용해 정확도를 높인다.
- 파이프라인이 깊을수록 misprediction penalty가 커지므로 고클럭 CPU에서 특히 중요하다.
- 계산 문제에서는 "분기 명령 비율 × 예측 실패율 × 실패 비용"을 CPI 증가 요인으로 해석하면 된다.

## 기출 포인트

- 파이프라인은 지연시간보다 처리량 향상 효과가 크다.
- 데이터 해저드는 포워딩으로 완화할 수 있지만 모든 경우를 제거하지는 못한다.
- 분기 예측 실패는 제어 해저드의 대표 비용이다.
- load-use 해저드가 주어지면 실제로 몇 개의 스톨이 필요한지 단계별로 그려 보는 문제가 자주 나온다.
- "파이프라인 도입 후 성능이 왜 항상 배수로 늘지 않는가"를 물으면 해저드와 불균형한 단계 시간을 근거로 답하면 된다.

## 핵심 개념

![14-1. 데이터패스와 제어장치 SVG](https://cs.chamung.com/public/wiki-assets/14-1-datapath-control.svg)
> 그림: 제어장치가 데이터패스의 PC, 레지스터 파일, ALU, 메모리 접근을 어떻게 제어하는지 보여주는 SVG.
> 출처: 내부 생성 자산 (`https://cs.chamung.com/public/wiki-assets/14-1-datapath-control.svg`)

- 명령어 실행은 fetch → decode → execute → memory access → write back 흐름으로 설명한다. 제어장치는 명령어를 해석해 데이터패스의 레지스터, ALU, 메모리 접근을 제어한다.
- 파이프라이닝은 여러 명령어의 단계를 겹쳐 처리량을 높이지만 hazard를 만든다. Structural hazard는 하드웨어 자원 충돌, data hazard는 이전 결과가 아직 준비되지 않은 경우, control hazard는 분기 결과를 알기 전 다음 명령어를 가져오는 경우다.
- Data hazard는 forwarding과 stall로 줄이고, control hazard는 branch prediction과 pipeline flush로 다룬다. 파이프라인은 단일 명령어 지연시간보다 전체 처리량 개선에 초점을 둔다.
- 예를 들어 명령어 10개, CPI 2, 클럭 주기 1ns이면 CPU time은 `10 × 2 × 1ns = 20ns`다. 성능 개선 답안에서는 instruction count, CPI, clock 중 어느 요소가 줄었는지 명시한다.

```text
CPU time = Instruction Count × CPI × Clock Cycle Time
```

- 파이프라인 최적화는 보통 CPI를 낮추는 쪽에 가깝다.
- 캐시 미스나 분기 실패가 늘어나면 이상적 CPI 1과 실제 CPI 사이 간격이 커진다.

## 약어 풀이

- CPU: Central Processing Unit, 중앙처리장치
- IF: Instruction Fetch, 명령어 인출
- ID: Instruction Decode, 명령어 해독
- EX: Execute, 실행 단계
- MEM: Memory Access, 메모리 접근
- WB: Write Back, 결과 기록
- ILP: Instruction Level Parallelism, 명령어 수준 병렬성
