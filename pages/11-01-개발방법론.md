# 11-01. 개발방법론

> 학습 목적: 폭포수, 애자일, 나선형 등 주요 개발방법론의 특징과 장단점을 비교한다.

## 핵심 개념

- 개발방법론은 요구사항 분석부터 설계, 구현, 테스트, 배포, 유지보수까지의 작업 절차와 관리 방식을 정한 체계다.
- 폭포수(Waterfall)는 순차적 진행과 문서화를 중시하고, 애자일(Agile)은 반복 개발과 피드백을 중시한다.
- 나선형(Spiral)은 반복 개발에 위험 분석을 결합한 모델로, 대규모·고위험 프로젝트에 적합하다.

### 서술형 확장 개념

- 요구공학은 요구사항 도출, 분석, 명세, 검증, 관리의 흐름으로 진행된다. 기능 요구사항은 시스템이 해야 할 동작이고, 비기능 요구사항은 성능, 보안, 가용성, 사용성처럼 품질 제약을 뜻한다.
- UML은 이해관계자 간 공통 언어 역할을 한다. Use case diagram은 사용자 목표와 시스템 범위, class diagram은 정적 구조, sequence diagram은 객체 간 메시지 흐름, activity diagram은 업무 절차를 표현한다.
- 애자일은 문서를 없애는 방법론이 아니라 변화 대응과 동작 소프트웨어를 중시하는 접근이다. 금융권처럼 감사·규제가 중요한 환경에서는 애자일을 쓰더라도 요구사항 추적성, 변경 이력, 승인 기록을 함께 관리해야 한다.

## 폭포수 모델(Waterfall)

폭포수 모델은 요구사항 분석 → 설계 → 구현 → 테스트 → 운영·유지보수 단계를 순서대로 진행한다.

### 특징

- 각 단계가 명확히 구분되고 산출물이 문서로 남는다.
- 이전 단계가 완료되어야 다음 단계로 넘어가는 구조다.
- 요구사항이 안정적이고 변경 가능성이 낮은 프로젝트에 적합하다.

### 장점과 단점

| 장점 | 단점 |
| --- | --- |
| 관리와 일정 예측이 쉽다 | 요구사항 변경에 약하다 |
| 단계별 산출물이 명확하다 | 후반에 오류를 발견하면 수정 비용이 크다 |
| 계약·감사·문서 중심 환경에 적합하다 | 사용자의 피드백 반영이 늦다 |

## 애자일 방법론(Agile)

애자일은 짧은 반복 주기 안에서 동작 가능한 소프트웨어를 만들고, 사용자 피드백을 반영하며 점진적으로 개선하는 접근이다.

### 특징

- 반복적·점진적 개발을 수행한다.
- 고객 참여와 빠른 피드백을 중시한다.
- 문서보다 동작하는 소프트웨어와 변화 대응을 강조한다.

### 장점과 단점

| 장점 | 단점 |
| --- | --- |
| 요구사항 변경에 유연하다 | 범위 관리가 어려울 수 있다 |
| 빠른 피드백으로 사용자 만족도를 높인다 | 팀 역량과 고객 참여도가 중요하다 |
| 초기부터 동작 결과물을 확인할 수 있다 | 대규모 조직에서는 조율 비용이 커질 수 있다 |

## 나선형 모델(Spiral)

나선형 모델은 계획 수립 → 위험 분석 → 개발·검증 → 고객 평가 과정을 반복한다. 보헴(Boehm)이 제안한 모델로, 위험 관리가 핵심이다.

### 특징

- 반복 개발을 하되 매 반복마다 위험을 분석한다.
- 프로토타입을 활용해 요구사항과 위험을 줄일 수 있다.
- 비용이 크고 복잡한 프로젝트에 적합하다.

## 스크럼(Scrum)

스크럼은 애자일 방법론의 대표 프레임워크로, 스프린트 단위로 계획·개발·검토를 반복한다.

| 구성 요소 | 설명 |
| --- | --- |
| 제품 책임자(Product Owner) | 제품 백로그 우선순위를 정하고 요구사항을 관리한다 |
| 스크럼 마스터(Scrum Master) | 팀이 스크럼 원칙을 따르도록 돕고 장애물을 제거한다 |
| 개발팀 | 스프린트 목표를 달성하기 위해 개발을 수행한다 |
| 제품 백로그 | 구현할 기능과 요구사항 목록 |
| 스프린트 백로그 | 해당 스프린트에서 수행할 작업 목록 |
| 일일 스크럼 | 짧은 일일 회의로 진행 상황과 장애물을 공유 |
| 스프린트 리뷰·회고 | 결과물을 검토하고 프로세스를 개선 |

## 칸반(Kanban)

칸반은 작업 흐름을 시각화하고 진행 중 작업(WIP: Work In Progress)을 제한해 병목을 줄이는 방식이다.

- 칸반 보드: To Do, Doing, Done 등 상태별 작업을 시각화한다.
- WIP 제한: 동시에 처리하는 작업 수를 제한해 흐름을 안정화한다.
- 지속적 개선: 고정 스프린트보다 흐름 기반 개선에 초점을 둔다.

## UP, RAD, XP

### UP(Unified Process)

UP는 반복적·점진적 개발 프로세스로, 유스케이스 중심·아키텍처 중심·위험 중심이라는 특징이 있다.

| 단계 | 핵심 내용 |
| --- | --- |
| Inception(도입) | 비전, 범위, 타당성 검토 |
| Elaboration(정련) | 주요 요구사항과 아키텍처 확정, 위험 감소 |
| Construction(구축) | 기능 구현과 테스트 |
| Transition(전이) | 배포, 사용자 교육, 운영 전환 |

### RAD(Rapid Application Development)

RAD는 빠른 개발을 목표로 프로토타이핑, 사용자 참여, CASE 도구 활용을 강조한다.

- 장점: 개발 기간 단축, 사용자 피드백 빠른 반영
- 단점: 대규모·고성능·복잡 시스템에는 부적합할 수 있음

### XP(eXtreme Programming)

XP는 애자일 방법론 중 개발 실천 기법을 강하게 강조한다.

- 짝 프로그래밍(Pair Programming)
- 테스트 주도 개발(TDD)
- 지속적 통합(CI)
- 리팩터링
- 단순 설계
- 고객 상주

## 방법론 비교표

| 방법론 | 핵심 키워드 | 적합한 상황 | 주의할 단점 |
| --- | --- | --- | --- |
| 폭포수 | 순차, 문서화, 단계별 산출물 | 요구사항이 안정적인 프로젝트 | 변경 대응 어려움 |
| 애자일 | 반복, 피드백, 변화 대응 | 요구사항 변화가 잦은 프로젝트 | 범위·일정 통제 어려움 |
| 나선형 | 위험 분석, 반복, 프로토타입 | 대규모·고위험 프로젝트 | 비용과 관리 복잡도 증가 |
| 스크럼 | 스프린트, 백로그, 역할 | 팀 단위 반복 개발 | 형식만 도입하면 효과 낮음 |
| 칸반 | 작업 흐름 시각화, WIP 제한 | 운영·유지보수, 지속적 업무 | 장기 계획 수립은 별도 관리 필요 |
| UP | 유스케이스, 아키텍처, 반복 | 객체지향·대규모 프로젝트 | 절차가 무거워질 수 있음 |
| RAD | 빠른 프로토타입, 사용자 참여 | 단기 개발, 화면 중심 시스템 | 품질·확장성 관리 필요 |
| XP | TDD, 짝 프로그래밍, CI | 변화가 빠른 소규모·중규모 팀 | 팀 성숙도 의존 |

## 약어 풀이

- IT: Information Technology, 정보기술
- RAD: Rapid Application Development, 신속 애플리케이션 개발
- UP: Unified Process, 통합 프로세스
- WIP: Work In Progress, 진행 중 작업
- XP: eXtreme Programming, 익스트림 프로그래밍
