# 11-01. 개발방법론

> 학습 목적: 폭포수, 애자일, 나선형 등 주요 개발방법론의 특징과 장단점을 비교한다.

> 연결 핵심정리: [04-3-소프트웨어공학-운영체제-컴퓨터구조](04-03-소프트웨어공학-운영체제-컴퓨터구조.md)

## 핵심 개념

- 개발방법론은 요구사항 분석부터 설계, 구현, 테스트, 배포, 유지보수까지의 작업 절차와 관리 방식을 정한 체계다.
- 큰 분류: 순차적(예: 폭포수), 반복적·증분(예: 애자일, 스크럼, 칸반), 위험 중심(예: 나선형), 아키텍처·유스케이스 중심(예: UP) 등.
- 방법론 선택 기준: 요구사항 안정성, 프로젝트 규모·복잡도, 조직 성숙도, 규제·감사 요구, 리스크 허용 수준 등.
- 핵심 용어
  - 요구사항(Functional vs Non-functional): 기능 요구는 시스템의 동작, 비기능 요구는 성능/보안/가용성/사용성 등 품질 속성.
  - 산출물: 요구명세서, 설계문서, 테스트케이스, 배포계획, 운영절차 등.
  - 반복·증분(Iterative & Incremental): 작은 단위로 동작하는 결과물을 자주 제공해 피드백을 반영.

### 서술형 확장 개념

- 요구공학 흐름: 도출(elicitation) → 분석 → 명세(specification) → 검증(verification) → 관리(traceability). 시험에서는 각 단계의 목적과 산출물을 묻는 문제가 자주 출제된다.
- UML의 역할: 요구·설계를 시각화하여 이해관계자 간 공통 언어를 제공. 주로 출제되는 다이어그램: 유스케이스(사용자 관점), 클래스(정적구조), 시퀀스(메시지 흐름), 액티비티(업무흐름).
- 애자일 오해 정리: 애자일은 ‘문서 최소화’가 아니라 ‘필요한 문서를 효율적으로 유지’하는 것이다. 특히 규제가 많은 분야(금융, 공공)에서는 요구추적성(traceability), 변경이력, 승인 증빙을 반드시 보완해야 한다.

## 폭포수 모델(Waterfall)

폭포수 모델은 요구사항 분석 → 설계 → 구현 → 테스트 → 운영·유지보수 단계를 순서대로 진행한다.

### 특징

- 단계별로 명확한 경계와 산출물이 존재한다.
- 다음 단계로 넘어가기 전 산출물 검증을 통해 진행 제어.
- 요구사항이 고정되어 있고 변경 가능성이 낮은 프로젝트에 적합.

### 장점과 단점

| 장점 | 단점 |
| --- | --- |
| 관리와 일정 예측이 쉽다 | 요구사항 변경에 약하다 |
| 단계별 산출물이 명확하다 | 후반에 오류를 발견하면 수정 비용이 크다 |
| 계약·감사·문서 중심 환경에 적합하다 | 사용자의 피드백 반영이 늦다 |

실무 적용 팁:
- 규제가 엄격한 금융·공공 프로젝트에서 계약 명세와 트레이스 가능한 산출물을 확보할 때 유리.
- 변경 통제(Change Control) 프로세스와 테스트 계획을 조기에 수립해야 후반 비용을 줄일 수 있다.

시험 포인트:
- ‘요구사항 변경이 잦은 프로젝트에 부적합한 이유’를 구조적 비용 관점으로 설명할 수 있어야 한다.
- 각 단계의 산출물(예: 요구명세서, 상세설계서, 테스트계획)의 목적을 서술하는 문제가 출제될 수 있다.

## 애자일 방법론(Agile)

애자일은 짧은 반복 주기 안에서 동작 가능한 소프트웨어를 만들고, 사용자 피드백을 반영하며 점진적으로 개선하는 접근이다.

### 특징

- 반복적·증분적 개발을 수행한다.
- 고객·사용자 참여와 빠른 피드백을 중시한다.
- 문서보다 동작하는 소프트웨어와 변화 대응을 강조한다.

### 장점과 단점

| 장점 | 단점 |
| --- | --- |
| 요구사항 변경에 유연하다 | 범위 관리가 어려울 수 있다 |
| 빠른 피드백으로 사용자 만족도를 높인다 | 팀 역량과 고객 참여도가 중요하다 |
| 초기부터 동작 결과물을 확인할 수 있다 | 대규모 조직에서는 조율 비용이 커질 수 있다 |

실무 적용 팁:
- 규제 환경에서는 요구추적성 매핑(요구→개발→테스트)을 자동화 도구와 연계해 보완해야 한다.
- CI(지속적 통합), 자동화 테스트, 배포파이프라인을 통해 빈번한 배포·검증을 안전하게 수행할 수 있다.

시험 포인트:
- 애자일의 원칙(예: 고객과의 협력, 변화 수용)을 사례에 적용해 설명하는 문제가 출제된다.
- 애자일 vs 폭포수의 비교: 장단점과 조직적 요구(규모, 규제, 고객 참여)를 근거로 방법론을 추천하라는 문항이 자주 나온다.

## 나선형 모델(Spiral)

나선형 모델은 계획 수립 → 위험 분석 → 개발·검증 → 고객 평가 과정을 반복한다. 보헴(Boehm)이 제안한 모델로, 위험 관리가 핵심이다.

### 특징

- 반복 개발을 하되 매 반복마다 위험(기술적·관리적·비용적)을 분석해 대응책을 세운다.
- 프로토타입을 적극 활용하여 요구사항과 기술 불확실성을 줄인다.
- 대규모·고위험 프로젝트에 적합하지만 관리·비용 부담이 크다.

실무 적용 팁:
- 고위험 요소(성능 요구, 보안 요건, 외부 연동 등)를 식별하고 우선순위를 둬 반복마다 검증한다.
- 프로토타입으로 사업성·기술성 검증을 먼저 수행해 전체 리스크를 낮춘다.

시험 포인트:
- 나선형의 각 반복 단계에서 수행하는 활동과 산출물을 정리할 수 있어야 한다.
- 위험 식별·평가·완화의 기본 원칙을 예시와 함께 설명하는 문제가 출제될 수 있다.

## 스크럼(Scrum)

스크럼은 애자일 방법론의 대표 프레임워크로, 스프린트 단위로 계획·개발·검토를 반복한다.

| 구성 요소 | 설명 |
| --- | --- |
| 제품 책임자(Product Owner) | 제품 백로그 우선순위를 정하고 요구사항을 관리한다 |
| 스크럼 마스터(Scrum Master) | 팀이 스크럼 원칙을 따르도록 돕고 장애물을 제거한다 |
| 개발팀 | 스프린트 목표를 달성하기 위해 개발을 수행한다 |
| 제품 백로그 | 구현할 기능과 요구사항 목록 |
| 스프린트 백로그 | 해당 스프린트에서 수행할 작업 목록 |
| 일일 스크럼 | 짧은 일일 회의로 진행 상황과 장애물을 공유 |
| 스프린트 리뷰·회고 | 결과물을 검토하고 프로세스를 개선 |

실무 적용 팁:
- 스프린트 길이(보통 1~4주)는 조직의 피드백 주기와 릴리스 주기를 고려해 결정.
- 회고(레트로스펙티브)를 통해 프로세스 문제를 해결하고 지속적으로 개선하는 문화를 정착시켜야 효과가 난다.

시험 포인트:
- 각 역할의 책임과 스크럼 행사(데일리, 리뷰, 회고)의 목적을 설명하라.
- 제품 백로그 우선순위 결정 기준(비즈니스 가치, 위험, 의존성)을 묻는 문제가 출제될 수 있다.

## 칸반(Kanban)

칸반은 작업 흐름을 시각화하고 진행 중 작업(WIP: Work In Progress)을 제한해 병목을 줄이는 방식이다.

- 칸반 보드: To Do, Doing, Done 등 상태별 작업을 시각화한다.
- WIP 제한: 동시에 처리하는 작업 수를 제한해 흐름을 안정화한다.
- 지속적 개선: 고정 스프린트보다 흐름 기반 개선에 초점을 둔다.

실무 적용 팁:
- 운영·유지보수나 요청 기반 작업(서비스 티켓)에 적합하다. SLA 기준으로 우선순위를 시각화하면 효과적이다.
- 흐름 지표(평균 처리 시간, 병목 현상, 처리율)를 측정해 병목을 해소한다.

시험 포인트:
- 칸반의 핵심 원칙(시각화, WIP 제한, 흐름 관리)을 예시와 함께 설명할 수 있어야 한다.

## UP, RAD, XP

### UP(Unified Process)

UP는 반복적·점진적 개발 프로세스로, 유스케이스 중심·아키텍처 중심·위험 중심이라는 특징이 있다.

| 단계 | 핵심 내용 |
| --- | --- |
| Inception(도입) | 비전, 범위, 타당성 검토 |
| Elaboration(정련) | 주요 요구사항과 아키텍처 확정, 위험 감소 |
| Construction(구축) | 기능 구현과 테스트 |
| Transition(전이) | 배포, 사용자 교육, 운영 전환 |

실무 적용 팁:
- 아키텍처 중심 접근이 필요할 때(대규모·장기 프로젝트) UP의 단계적 검증이 유리하다.
- 각 단계에서 아키텍처 결정사항을 문서화해 이후 이관과 유지보수를 용이하게 해야 한다.

시험 포인트:
- 각 단계별 목표와 산출물을 구분해 서술하는 문제가 자주 출제된다.

### RAD(Rapid Application Development)

RAD는 빠른 개발을 목표로 프로토타이핑, 사용자 참여, CASE 도구 활용을 강조한다.

- 장점: 개발 기간 단축, 사용자 피드백 빠른 반영
- 단점: 대규모·고성능·복잡 시스템에는 부적합할 수 있음

실무 적용 팁:
- 화면 중심의 업무 시스템(예: 내부 툴, 폼 기반 앱)에서 빠르게 프로토타입을 만들어 검증할 때 유리하다.
- 확장성·품질 관리 계획을 별도로 마련하지 않으면 유지보수 부담이 커질 수 있다.

시험 포인트:
- RAD의 핵심 기법(프로토타이핑·사용자 참여)의 장단점을 실제 사례와 연결해 설명하라.

### XP(eXtreme Programming)

XP는 애자일 방법론 중 개발 실천 기법을 강하게 강조한다.

- 핵심 실천사항:
  - 짝 프로그래밍(Pair Programming)
  - 테스트 주도 개발(TDD)
  - 지속적 통합(CI)
  - 리팩터링
  - 단순 설계
  - 고객 상주(On-site Customer)

실무 적용 팁:
- 코드 품질과 변경 대응성을 높이는 데 효과적이지만 팀 문화와 규율(테스트 작성, 코드리뷰)이 필수적이다.
- TDD와 CI를 조직 표준으로 만들면 회귀 결함을 줄일 수 있다.

시험 포인트:
- TDD의 사이클(Red-Green-Refactor)과 기대 효과를 설명하라.
- 짝 프로그래밍의 장단점을 조직 관점에서 비교하라.

## 방법론 비교표

| 방법론 | 핵심 키워드 | 적합한 상황 | 주의할 단점 |
| --- | --- | --- | --- |
| 폭포수 | 순차, 문서화, 단계별 산출물 | 요구사항이 안정적인 프로젝트 | 변경 대응 어려움 |
| 애자일 | 반복, 피드백, 변화 대응 | 요구사항 변화가 잦은 프로젝트 | 범위·일정 통제 어려움 |
| 나선형 | 위험 분석, 반복, 프로토타입 | 대규모·고위험 프로젝트 | 비용과 관리 복잡도 증가 |
| 스크럼 | 스프린트, 백로그, 역할 | 팀 단위 반복 개발 | 형식만 도입하면 효과 낮음 |
| 칸반 | 작업 흐름 시각화, WIP 제한 | 운영·유지보수, 지속적 업무 | 장기 계획 수립은 별도 관리 필요 |
| UP | 유스케이스, 아키텍처, 반복 | 객체지향·대규모 프로젝트 | 절차가 무거워질 수 있음 |
| RAD | 빠른 프로토타입, 사용자 참여 | 단기 개발, 화면 중심 시스템 | 품질·확장성 관리 필요 |
| XP | TDD, 짝 프로그래밍, CI | 변화가 빠른 소규모·중규모 팀 | 팀 성숙도 의존 |

실무 선택 체크리스트:
- 요구사항의 안정성: 안정적 → 폭포수 / 불확실 → 애자일·나선형
- 규제·감사 필요성: 높음 → 문서·추적성 확보(폭포수 또는 애자일 + 추가 통제)
- 프로젝트 규모·위험: 대규모·고위험 → 나선형·UP
- 운영/유지보수 중심: 칸반 고려
- 팀 성숙도: 성숙도 낮음 → 절차화된 방법론 또는 혼합 접근 권장

## 시험 포인트 요약

- 방법론 정의와 장단점을 사례로 설명할 수 있어야 한다.
- 특정 상황(예: 규제 많은 금융사, 짧은 납기, 운영성 이슈)에 맞는 방법론을 추천하고 그 이유를 제시하라.
- 스크럼의 역할과 행사, 칸반의 WIP 원리, 나선형의 위험 관리 흐름 등은 빈출 주제다.
- 요구공학(도출→분석→명세→검증)과 UML 다이어그램별 용도는 서술형으로 출제될 가능성이 높다.

## 실무 연결(현업 적용 체크리스트)

- 요구추적성: 요구→설계→코드→테스트 매핑을 자동화해 변경영향을 관리하라.
- 품질 확보: TDD, 코드리뷰, CI/CD 파이프라인, 자동화 테스트로 회귀 위험을 줄인다.
- 규제·감사 대응: 변경 승인 기록, 테스트 결과 보관, 릴리스 노트 등 증빙 자료를 구조화하라.
- 혼합 모델 적용: 현실에서는 하이브리드(폭포수+애자일, 스크럼+칸반 등)로 적용하는 경우가 많다. 중요 것은 원칙과 산출물의 충실성이다.

## 약어 풀이

- IT: Information Technology, 정보기술
- RAD: Rapid Application Development, 신속 애플리케이션 개발
- UP: Unified Process, 통합 프로세스
- WIP: Work In Progress, 진행 중 작업
- XP: eXtreme Programming, 익스트림 프로그래밍
