# 11-02-01. 블랙박스와 화이트박스

> 학습 목적: 블랙박스 테스트와 화이트박스 테스트의 관점, 대표 기법, 커버리지 기준을 구분한다.
> 관련 기출: [05-금융공기업-IT-기출문제-239제](05-금융공기업-IT-기출문제-239제.md)
> 연결 핵심정리: [04-3-소프트웨어공학-운영체제-컴퓨터구조](04-03-소프트웨어공학-운영체제-컴퓨터구조.md)

## 핵심 개념

- 블랙박스 테스트는 내부 구조(코드, 설계)를 보지 않고 요구사항·명세·입출력에 기반해 테스트한다. 사용자 관점에서 기능의 완전성(명세 대비 동작)을 검증하는 데 적합하다.
- 화이트박스 테스트는 코드의 제어 흐름, 분기, 조건, 반복 구조를 분석해 테스트 케이스를 설계한다. 개발자 관점에서 구조적 결함(예: 분기 누락, 논리 오류)을 찾는 데 유리하다.
- 블랙박스의 대표 기법: 동치분할, 경계값 분석, 결정 테이블, 상태 전이 테스트, 유스케이스 테스트.
- 화이트박스의 대표 기준: 문장(Statement) 커버리지, 분기(Branch/Decision) 커버리지, 조건(Condition) 커버리지, 경로(Path) 커버리지.

### 서술형 확장 개념

- 동치분할은 입력 공간을 동일한 동작을 낳는 블록(파티션)으로 나눈 뒤 각 블록에서 하나 또는 소수의 대표 입력만 선택해 테스트 수를 줄인다. 시험에서 "대표값 선정 이유"를 물을 때는 동일 처리 결과가 기대된다는 점을 근거로 설명한다.
- 경계값 분석은 입력의 경계(최솟값, 최댓값, 허용 범위 바로 밖/안의 값)에서 오류 발생 확률이 높다는 경험적 사실을 이용한다. 시험에서는 경계 주변의 값(경계-1, 경계, 경계+1)을 나열하고 그 이유를 쓰는 문제가 자주 출제된다.
- 결정 테이블은 다수의 입력 조건 조합이 서로 다른 결과를 낳는 규칙형 문제에서 유용하다. 모든 조합을 검사하기 어려울 때는 유의미한 룰(상호 배타성, 우선순위)을 기준으로 축소한다.
- 상태 전이 테스트는 시스템이 상태를 가지며 이벤트에 따라 상태가 변하고 그에 따라 허용되는 동작이 달라질 때 효과적이다(예: 로그인 실패 횟수에 따른 계정 잠금, 송금 상태 흐름). 상태, 이벤트, 전이, 전이 시 제약을 명확히 표기해 테스트 케이스를 만든다.
- Statement/Branch/Condition/Path 커버리지 간의 관계를 이해하면 출제·실무에서 유리하다. 일반적으로 문장 < 분기 < 조건 < 경로의 포괄성이 증가하지만 비용과 복잡도도 증가한다.

## 블랙박스 테스트

블랙박스 테스트는 프로그램 내부 코드가 어떻게 작성되었는지 보지 않고, 요구사항 명세에 따라 입력에 대한 출력이 올바른지 확인한다. 사용자 시나리오, 비즈니스 규칙, 인터페이스 요구사항 검증에 적합하다.

### 대표 기법

| 기법 | 설명 | 예시 |
| --- | --- | --- |
| 동치분할(Equivalence Partitioning) | 입력값을 같은 결과가 예상되는 집합으로 나누고 대표값을 테스트 | 나이 0~120 입력에서 유효/무효 구간 분리 |
| 경계값 분석(Boundary Value Analysis) | 오류가 자주 발생하는 경계 근처 값을 테스트 | 1~100 허용이면 0, 1, 2, 99, 100, 101 확인 |
| 결정 테이블(Decision Table) | 여러 조건 조합과 결과를 표로 정리해 테스트 | 할인 조건, 회원 등급, 쿠폰 사용 여부 조합 |
| 상태 전이 테스트 | 상태 변화와 이벤트를 기준으로 테스트 | 로그인 실패 횟수에 따른 계정 잠금 |
| 유스케이스 테스트 | 사용자 시나리오 흐름을 기준으로 테스트 | 회원 가입, 결제, 승인 요청 흐름 |

실무 팁:
- 요구사항이 불분명할 때는 블랙박스 기법으로 우선 명세 위반(누락·오류)을 찾아 요구사항을 정제한다.
- 자동화가 쉬운 케이스(경계값, 동치 대표값)는 테스트 자동화 대상에 포함시키고, 상태 전이·유스케이스는 시나리오 기반 자동화 또는 수동 검증으로 보완한다.

시험 포인트:
- 동치분할과 경계값 분석의 차이(대표값 vs 경계 집중)를 명확히 설명할 것.
- 결정 테이블에서의 축소 방법(무의미한 조합 제거, 우선순위 규칙) 및 상태 전이의 상태·이벤트 표기법을 묻는 문제가 자주 출제됨.

## 화이트박스 테스트

화이트박스 테스트는 코드 내부의 분기, 반복, 조건, 실행 경로를 확인한다. 개발자가 작성한 로직의 분기 누락, 잘못된 조건 사용, 예외 처리 미흡 등을 발견하는 데 유리하다.

### 커버리지 기준

| 기준 | 의미 | 특징 |
| --- | --- | --- |
| 문장 커버리지(Statement Coverage) | 모든 문장이 최소 1번 실행되는지 확인 | 가장 약한 구조 기반 기준; 단순 미실행 코드 발견에 유리 |
| 분기 커버리지(Branch/Decision Coverage) | 각 분기의 참·거짓이 최소 1번 실행되는지 확인 | if, switch 분기 누락을 찾기 좋음; 분기별 결과 조합을 고려 |
| 조건 커버리지(Condition Coverage) | 복합 조건의 각 개별 조건이 참·거짓을 갖는지 확인 | 분기보다 세부 조건에 초점; 각 원자 조건의 진리값 조합 검토 필요 |
| 경로 커버리지(Path Coverage) | 가능한 실행 경로를 확인 | 완전 수행은 현실적으로 어려움(루프, 외부 조건으로 인한 경로 폭발) |

실무 팁:
- 분기 커버리지를 달성해도 복합 조건의 결함이 남을 수 있으므로 조건 커버리지도 고려한다.
- 루프와 예외 처리 경로는 별도로 설계해 테스트 케이스에 포함한다(예: 0회 반복, 1회 반복, 다회 반복).
- 코드 커버리지 도구를 사용하면 자동 측정·리포팅이 가능하지만, 높은 수치 자체가 결함 없음의 보증은 아니다. 논리적 테스트 케이스의 품질을 함께 검토해야 한다.

시험 포인트:
- 문장·분기·조건 커버리지의 정의와 예시를 직접 그려 설명할 수 있어야 한다.
- 경로 커버리지의 어려움(무한 루프, 분기 조합 폭발)을 설명하고 현실적인 대안(제한적 경로 선택, 결정적 경로 우선순위)을 제시할 수 있어야 한다.

## 통합(Integration) 테스트 관점: Top-down, Bottom-up, Sandwich

- Top-down: 상위 모듈부터 통합하며 하위 모듈을 stub으로 대체한다. 사용자 관점 인터페이스 우선 검증에 유리하며, 상위 설계 결함을 조기에 발견할 수 있다.
- Bottom-up: 하위 모듈부터 통합하며 상위 호출자를 driver로 대체한다. 성능·저수준 로직 검증에 유리하다.
- Sandwich(또는 Hybrid): 상·하부를 병행하여 중앙에서 통합하는 방식으로, 두 방식의 장점을 조합하려는 실무적 접근이다.

실무 팁:
- 모듈 간 인터페이스가 복잡하면 Top-down으로 인터페이스 명세를 먼저 검증하고, 하위 로직은 Bottom-up으로 검증해 통합 리스크를 줄인다.
- Stub/Driver 작성 비용과 유지보수성을 고려해 테스트 레벨을 설계한다.

## 비교표

| 구분 | 블랙박스 테스트 | 화이트박스 테스트 |
| --- | --- | --- |
| 기준 | 요구사항, 명세, 입출력 | 코드 구조, 분기, 조건, 경로 |
| 내부 코드 이해 | 필요 없음 | 필요함 |
| 수행 관점 | 사용자·테스터 관점 | 개발자·구조 분석 관점 |
| 대표 기법 | 동치분할, 경계값 분석, 결정 테이블 | 문장·분기·조건·경로 커버리지 |
| 발견하기 쉬운 결함 | 누락 기능, 명세 불일치, 경계 오류 | 논리 오류, 분기 누락, 경로 오류 |

요약 팁:
- 블랙박스는 "무엇(What)"을 확인: 요구사항이 제대로 구현됐는가?
- 화이트박스는 "어떻게(How)"를 확인: 내부 로직이 의도대로 동작하는가?
- 실무에서는 두 방식의 조합(기능 검증은 블랙박스, 구조적 결함은 화이트박스로 보완)이 가장 효과적이다.
