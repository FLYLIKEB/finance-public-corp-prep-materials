# 07-04. 트랜잭션과 회복

> 학습 목적: ACID와 회복 기법의 목적을 정리한다.
> 관련 기출: [05-10-데이터베이스-기출-모음](05-10-데이터베이스-기출-모음.md)
> 연결 핵심정리: [04-5-자료구조-알고리즘-DB-금융IT](04-05-자료구조-알고리즘-DB-금융IT.md)

## 핵심 개념

- 트랜잭션은 논리적 작업 단위다. (예: 은행 이체: A에서 출금하고 B에 입금하는 두 작업을 하나의 단위로 묶음)
- ACID는 원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 지속성(Durability)이다.
- 회복은 시스템 장애나 오류 발생 후 데이터베이스를 일관된 상태로 되돌리는 과정이다.


### 서술형 확장 개념

- 격리 수준은 동시성과 일관성의 trade-off다.
  - Read Uncommitted: dirty read 허용(동시성 최고, 일관성 최저)
  - Read Committed: 커밋된 값만 읽음(Dirty read 방지). 그러나 non-repeatable read 가능
  - Repeatable Read: 같은 행의 반복 읽기 일관성 보장(Non-repeatable read 방지), 하지만 phantom read 가능
  - Serializable: 모든 트랜잭션이 직렬로 실행된 것과 동일한 결과를 보장(일관성 최고, 동시성 최저)

- 주요 읽기 이상(Anomalies)
  - Dirty read: 트랜잭션 T1이 아직 커밋하지 않은 값을 T2가 읽는 경우. T1이 롤백되면 T2는 잘못된 값을 기반으로 연산함.
  - Non-repeatable read: 같은 트랜잭션 내에서 같은 행을 두 번 읽었을 때 값이 달라지는 경우(다른 트랜잭션이 중간에 수정하고 커밋했음).
  - Phantom read: 같은 조건으로 질의했는데 행의 집합이 달라지는 현상(중간에 다른 트랜잭션이 조건에 맞는 행을 삽입/삭제함).

- 직렬가능성(Conflict serializability)
  - 개념: 충돌(conflict)하는 연산(예: 동일한 데이터에 대한 읽기/쓰기 중 하나가 쓰기인 경우)의 상대적 순서를 보존하여 어떤 직렬 스케줄과 동등한지 판단.
  - 판정법: precedence graph(또는 conflict graph)에 사이클이 없으면 conflict-serializable.

- 회복의 핵심: WAL(Write-Ahead Logging)
  - 원칙: 데이터베이스 페이지를 디스크에 쓰기 전에 로그를 먼저 디스크에 기록한다.
  - 목적: 장애 후 로그를 보고 undo와 redo를 통해 원자성과 지속성을 보장.

- 체크포인트(Checkpoint)
  - 목적: 복구 시 로그를 확인해야 하는 범위를 줄임.
  - 동작: 특정 시점의 로그 위치와 디스크에 반영된 트랜잭션 상태를 기록하여 이후 복구 비용을 낮춤.

- 버퍼 정책: steal/no-steal, force/no-force
  - Steal vs No-steal: 버퍼가 더티 페이지(미커밋 변경)를 디스크로 언제 쓸 수 있는가의 차이
  - Force vs No-force: 트랜잭션 커밋 시 변경된 페이지를 강제로 디스크에 쓰는지의 여부
  - 정책 조합에 따라 undo/redo 필요 여부와 복구 알고리즘 설계가 달라짐

시험 답안에 쓸 수 있는 간단 정의 예시(문장 형태)
- "원자성(Atomicity): 트랜잭션의 모든 연산은 전부 성공하거나 전부 실패하여 그 결과가 부분적으로 반영되지 않음을 보장한다."
- "격리성(Isolation): 동시에 실행되는 트랜잭션들이 서로의 중간 결과에 영향을 미치지 않아 각 트랜잭션이 마치 단독으로 실행된 것처럼 보이도록 보장한다."
- "WAL(Write-Ahead Logging): 데이터 페이지를 디스크에 기록하기 전에 변경 로그를 먼저 디스크에 기록하여 장애 복구 시 로그를 이용해 undo/redo를 수행할 수 있게 하는 기법이다."

간단 예시 (시험 답안으로 활용 가능)
- 은행 이체(원자성 예시): "A 계좌 -100원, B 계좌 +100원 두 연산을 하나의 트랜잭션으로 묶어 둘 중 하나라도 실패하면 둘 다 취소한다."

간단 시퀀스 예시 (WAL과 undo/redo 개념 설명용)
```sql
-- 트랜잭션 예시(의사 SQL)
BEGIN TRANSACTION; -- T1 시작
UPDATE account SET balance = balance - 100 WHERE id = 'A'; -- 로그 L1: A:-100
UPDATE account SET balance = balance + 100 WHERE id = 'B'; -- 로그 L2: B:+100
COMMIT; -- 커밋 로그 기록(L3)
```
- WAL 적용 원리: 위 UPDATE 수행 전 로그(L1, L2)가 디스크의 로그에 기록되어야 하며, 장애 시 이 로그를 보고 커밋 여부에 따라 redo(커밋된 트랜잭션) 또는 undo(미커밋 트랜잭션)를 수행한다.

| 회복 연산 | 쓰임 | 설명 |
| --- | --- | --- |
| Undo | 미완료 트랜잭션 취소 | 커밋 전 변경을 이전 값으로 되돌림 |
| Redo | 완료 트랜잭션 재반영 | 커밋됐지만 디스크 미반영 가능성이 있는 변경 재실행 |
| Checkpoint | 복구 범위 축소 | 특정 시점의 로그/버퍼 상태를 기록 |

추가 비교표 — 격리 수준별 허용 현상(간단 정리)

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read | 동시성 수준 |
| --- | ---: | ---: | ---: | ---: |
| Read Uncommitted | 허용 | 허용 | 허용 | 높음 |
| Read Committed | 불허 | 허용 | 허용 | 보통 |
| Repeatable Read | 불허 | 불허 | 허용 가능 | 낮음 |
| Serializable | 불허 | 불허 | 불허 | 매우 낮음 |

## 쉽게 이해하기

- 트랜잭션은 은행 이체처럼 중간에 끊기면 안 되는 작업 묶음이다. A 계좌 차감과 B 계좌 입금은 함께 성공하거나 함께 실패해야 한다.
- ACID는 거래가 안전하게 처리되기 위한 네 가지 약속이다. 특히 원자성은 “전부 성공 또는 전부 취소”를 뜻한다.
- 회복은 장애가 나도 장부를 맞는 상태로 되돌리는 기술이다.
