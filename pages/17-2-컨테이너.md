## 핵심 개념

- 컨테이너는 애플리케이션과 의존성을 이미지로 묶고, 호스트 OS 커널을 공유해 격리 실행하는 방식이다.
- Docker image는 불변 실행 패키지이고, container는 image의 실행 인스턴스다.
- Kubernetes는 컨테이너 배포, 서비스 발견, 스케일링, 롤링 업데이트, self-healing을 제공하는 오케스트레이션 플랫폼이다.
- VM과 비교하면 컨테이너는 가볍고 배포 속도가 빠르지만, 커널을 공유하므로 런타임 권한과 이미지 위생 관리가 매우 중요하다.
- 운영 관점에서는 이미지 빌드 표준화, 레지스트리 통제, 배포 전략, 관측성, 비밀정보 관리가 함께 설계되어야 한다.

| 구성 요소 | 역할 |
| --- | --- |
| Pod | 하나 이상의 컨테이너를 묶는 최소 배포 단위 |
| Deployment | 원하는 Pod 개수와 업데이트 전략 관리 |
| Service | Pod 집합에 안정적인 접근 지점 제공 |
| Ingress | 외부 HTTP/S 트래픽 라우팅 |
| ConfigMap/Secret | 설정과 민감정보 분리 |
| Namespace | 팀·서비스 단위 리소스 격리 |
| RBAC | 사용자·서비스 계정 권한 통제 |
| NetworkPolicy | Pod 간 통신 범위 제한 |

## 금융권 답안 포인트

컨테이너는 배포 일관성과 빠른 확장에 유리하지만 이미지 취약점, secret 관리, 런타임 권한, 네트워크 정책, 감사 로그가 중요하다. 금융 시스템에서는 CI/CD에서 이미지 서명과 취약점 스캔을 수행하고, 운영 클러스터에서는 namespace와 RBAC으로 권한을 분리한다.

- 장점: 환경 재현성, 빠른 롤아웃·롤백, 자원 효율성, 자동화 친화성
- 리스크: 취약한 베이스 이미지, 과도한 privileged 권한, 잘못된 시크릿 주입, east-west 트래픽 통제 실패
- 통제: admission policy, image registry 통제, node·namespace 분리, 감사 로그 수집, 배포 승인 절차

## 운영 체크리스트

- [ ] 베이스 이미지를 최소화하고 정기 취약점 스캔을 수행하는가?
- [ ] Secret을 이미지나 Git 저장소에 직접 넣지 않는가?
- [ ] readiness/liveness probe, requests/limits, 롤링 업데이트 정책이 정의되어 있는가?
- [ ] Namespace, RBAC, NetworkPolicy로 서비스 경계를 분리했는가?
- [ ] 배포 로그와 클러스터 이벤트를 중앙에서 추적할 수 있는가?

## 간단한 예시

```bash
docker build -t registry.example.com/payments/api:2026-07 .
docker push registry.example.com/payments/api:2026-07
kubectl rollout restart deployment/payments-api -n prod
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
```

## 실무 연결

- 금융 서비스는 배포 실패가 곧 서비스 장애와 민원으로 이어질 수 있어 blue-green 또는 rolling update 정책을 사전에 검증해야 한다.
- 컨테이너 자체보다 중요한 것은 운영 표준이다. 로그 포맷 통일, 헬스체크 기준, 리소스 요청값, 장애 시 롤백 기준이 없으면 클러스터가 빠르게 복잡해진다.
- 마이크로서비스 환경에서는 컨테이너 수가 급증하므로 서비스 메시·트레이싱까지 가지 않더라도 최소한 요청 ID 기반 추적은 확보해야 한다.
