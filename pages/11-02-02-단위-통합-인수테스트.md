# 11-02-02. 단위-통합-인수테스트

> 학습 목적: 단위, 통합, 시스템, 인수 테스트의 범위와 목적을 구분하고 회귀·스모크 테스트를 이해한다.

> 연결 핵심정리: [04-3-소프트웨어공학-운영체제-컴퓨터구조](04-03-소프트웨어공학-운영체제-컴퓨터구조.md)

## 핵심 개념

- 단위 테스트는 개별 모듈, 함수, 클래스를 검증한다.
- 통합 테스트는 모듈 사이의 인터페이스와 데이터 흐름을 검증한다.
- 시스템 테스트는 완성된 전체 시스템이 기능 및 비기능 요구사항을 만족하는지 확인한다.
- 인수 테스트는 사용자나 고객 관점에서 제공된 소프트웨어가 인수 기준(SLA, 규정 준수 등)을 충족하는지 판단한다.

## 단위 테스트(Unit Test)

단위 테스트는 가장 작은 개발 단위가 의도대로 동작하는지 검증한다. 금융공기업 환경에서는 회계·거래 로직의 정확성이 특히 중요하다.

- 대상: 함수, 메서드, 클래스, 모듈(예: 이체 금액 검증 함수, 이자 계산 모듈)
- 목적: 내부 로직 오류를 빠르게 발견하여 비용이 큰 결함으로 확산되는 것을 방지
- 특징: 빠르고 자동화하기 쉬우며 CI 파이프라인에서 빈번히 실행
- 보조 도구: Stub, Mock, Fake DB 등을 활용(예: 외부 결제 게이트웨이 대신 Mock 사용)
- 금융 예시: 소수점 반올림 규칙, 수수료 계산, 거래 상태 전이 검증

체크포인트:
- 경계값(최댓값/최솟값) 처리 검증
- 예외 처리 및 에러 메시지 검증
- 동시성 이슈가 예상되는 경우 경합 상황 단위 검증

## 통합 테스트(Integration Test)

통합 테스트는 여러 모듈을 연결했을 때 인터페이스와 데이터 흐름이 올바른지 확인한다. 금융 시스템에서는 트랜잭션 경계와 데이터 일관성이 핵심이다.

### 통합 방식

| 방식 | 설명 | 특징 |
| --- | --- | --- |
| 빅뱅 통합 | 모든 모듈을 한 번에 결합 | 단순하지만 오류 원인 추적이 어렵다. 작은 시스템에서만 권장. |
| 상향식 통합 | 하위 모듈부터 결합 | 상위 모듈 대체용 Driver가 필요할 수 있다. 하위 유닛 안정화에 유리. |
| 하향식 통합 | 상위 모듈부터 결합 | 하위 모듈 대체용 Stub이 필요할 수 있다. 초기 화면·API 흐름 검증에 유리. |
| 샌드위치 통합 | 상향식과 하향식을 병행 | 병렬 진행 가능하지만 테스트 관리가 복잡하다. 복합 서비스(채널·백오피스·결제)에서 사용. |

통합 테스트 고려사항(금융):
- DB 트랜잭션 격리 수준 확인(예: READ COMMITTED, REPEATABLE READ) 및 롤백 동작 검증
- 외부 연동(결제사, 신용평가, 공공 API) 응답 지연·오류 처리 검증
- 메시지 큐/배치 처리가 있는 경우 재시도·중복 처리 검증

## 시스템 테스트(System Test)

시스템 테스트는 완성된 소프트웨어 전체가 기능 요구사항과 비기능 요구사항을 만족하는지 확인한다. 금융서비스에서는 규제 준수, 데이터 정합성, 고가용성이 필수다.

- 기능 테스트: 요구 기능이 명세대로 동작하는지(예: 계좌조회, 이체, 정산 프로세스)
- 성능 테스트: 피크 시간대 동시 접속, 배치 창(야간 정산) 처리량, 응답 시간 SLA 확인
- 보안 테스트: 인증·인가 검증, 민감정보 암호화, 취약점(OWASP) 스캔, 감사로그 무결성 확인
- 사용성 테스트: 업무 사용자(텔러, 상담원) 관점의 화면 흐름·작업효율성 확인
- 호환성 테스트: 지원 OS, 네트워크 환경, 브라우저, 모바일 앱 버전 간 호환성 확인

예시 체크리스트(시스템 테스트):
- 핵심 업무 시나리오(계좌 개설 → 입금 → 이체 → 정산) 종단 간 검증
- 장애 전이 시 복구 시나리오(장애 감지 → 페일오버 → 데이터 일관성 확인)
- 백업·복구 정책 검증: 복구 시간(RTO)·복구 시점(RPO) 충족 여부

## 인수 테스트(Acceptance Test)

인수 테스트는 고객이나 사용자가 시스템을 받아들일 수 있는지 판단하는 테스트다. 금융공기업에서는 규제, 내부통제, 운영 절차 준수가 중요한 인수 기준이다.

| 유형 | 설명 |
| --- | --- |
| 알파 테스트 | 개발 조직 내부 또는 제한된 환경에서 사용자 관점으로 수행(운영 팀·업무 담당자 참여). 초기 사용성·운영 절차 검증에 사용. |
| 베타 테스트 | 실제 사용자 환경에서 제한된 사용자에게 배포해 수행(실거래 아닌 샌드박스 또는 제한된 실거래). 실환경 문제 발견에 유리. |
| 운영 인수 테스트 | 운영 절차, 백업, 복구, 모니터링, 운영자 매뉴얼·권한 설정 등을 실제 운영 환경에 근접하게 확인. 규제·감사 요건 충족 필요. |

인수 기준(예):
- 주요 업무 시나리오 통과(업무 담당자 서명 기준)
- 법적·규제 요구사항(로그 보관, 암호화, 접근 통제) 충족
- SLA 및 운영매뉴얼 승인

## 회귀 테스트와 스모크 테스트

### 회귀 테스트(Regression Test)

회귀 테스트는 변경 이후 기존 기능이 깨지지 않았는지 다시 확인하는 테스트다. 버그 수정, 기능 추가, 리팩터링 이후 수행한다. 금융에서는 특히 회계·정산·거래 무결성에 대한 회귀가 중요하다.

- 수행 시점: 기능 변경·버전 업데이트·패치 적용 후
- 범위 선정: 영향 범위 기반(모듈 의존도, 변경 파일 기준) 또는 전체 회귀(중요 릴리스 시)
- 자동화 권장: 반복적 수행으로 인간 실수 감소 및 빠른 피드백 확보

금융 예시: 이체 로직 수정 후 역잔액 발생 여부, 수수료 계산 변경에 따른 계정 분개 영향 검증

### 스모크 테스트(Smoke Test)

스모크 테스트는 빌드나 배포 직후 핵심 기능이 기본적으로 동작하는지 빠르게 확인하는 테스트다. 깊이 있는 검증보다 “더 진행할 수 있는 상태인지” 판단하는 목적이 크다.

- 수행 시점: CI 빌드 후, 배포 직후(스테이징/프로덕션 전환 직전)
- 범위: 로그인, 권한 체크, 핵심 트랜잭션(잔액조회·이체 요청), 주요 API 헬스 체크
- 목적: 배포 후 빠른 실패 감지로 롤백 또는 상세 테스트 수행 여부 결정

| 구분 | 회귀 테스트 | 스모크 테스트 |
| --- | --- | --- |
| 목적 | 변경 영향으로 기존 기능이 깨졌는지 확인 | 빌드·배포가 기본적으로 사용 가능한지 확인 |
| 범위 | 기존 기능 전반 또는 영향 범위(심층) | 핵심 기능 중심의 얕은 점검 |
| 시점 | 변경 후 반복 수행(자주/자동화) | 빌드·배포 직후 |
| 금융 핵심 예 | 정산·회계 종단검증, 데이터 무결성 | 로그인, 잔액조회, 송금 API 기초 동작 확인 |

## 테스트 레벨 비교표

| 구분 | 단위 테스트 | 통합 테스트 | 시스템 테스트 | 인수 테스트 |
| --- | --- | --- | --- | --- |
| 관점 | 개발자 | 개발자·테스터 | 테스터·품질·운영 | 사용자·고객·업무담당자 |
| 범위 | 개별 모듈(함수·클래스) | 모듈 간 연결(서비스·DB·외부 연계) | 전체 시스템(기능+비기능) | 인수 기준(SLA·규제·업무 절차) |
| 주요 결함 | 로직 오류, 연산 실수 | 인터페이스 오류, 트랜잭션 처리 실패 | 요구사항 불일치, 성능·보안 결함 | 사용자 요구 미충족, 운영 절차 미비 |
| 관련 키워드 | Mock, Stub, 단위 커버리지 | Driver, Stub, Big Bang, 트랜잭션 일관성 | 성능(Throughput), 보안, 배치 윈도우 | 알파, 베타, UAT, 규제 준수 |

## 약어 풀이

- IT: Information Technology, 정보기술
- OS: Operating System, 운영체제
- SLA: Service Level Agreement, 서비스 수준 계약(인수 기준에 자주 사용)
- RTO: Recovery Time Objective, 복구 목표 시간
- RPO: Recovery Point Objective, 복구 시점 목표
- UAT: User Acceptance Testing, 사용자 인수 테스트
