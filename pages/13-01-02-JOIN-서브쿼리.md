# 13-01-02. JOIN-서브쿼리

> 학습 목적: JOIN 결과와 서브쿼리 실행 의미를 파악한다.
> 관련 기출: [05-10-데이터베이스-기출-모음](05-10-데이터베이스-기출-모음.md)
> 연결 핵심정리: [04-2-프로그래밍-SQL-분산-클라우드](04-02-프로그래밍-SQL-분산-클라우드.md)

## 핵심 개념

- INNER JOIN은 매칭되는 행만 반환한다.
- OUTER JOIN은 한쪽의 미매칭 행도 보존한다. (LEFT, RIGHT, FULL)
- 서브쿼리는 다른 쿼리 안에 포함된 쿼리다. 비상관(subquery independent)과 상관(correlated) 서브쿼리로 나뉜다.


### 서술형 확장 개념

- JOIN은 논리적으로 테이블을 결합하지만, 물리적으로는 Nested Loop, Hash, Sort-Merge 같은 알고리즘으로 실행된다.
  - Nested Loop: 작은 입력(또는 인덱스가 잘 설계된 경우)에서 유리하다. 바깥쪽 행마다 인덱스 또는 테이블을 탐색한다.
  - Hash Join: 큰 테이블 간의 동등 조인에 유리하다. 메모리 내 해시 테이블을 만들고 매칭한다. 메모리 부족시 디스크로 스필될 수 있다.
  - Sort-Merge(또는 Merge Join): 양쪽 입력이 정렬되어 있을 때 효율적이다. 인덱스나 미리 정렬된 결과가 있으면 유리하다.
- 서브쿼리는 비상관 서브쿼리와 상관 서브쿼리로 나뉜다.
  - 비상관 서브쿼리: 한 번 실행되어 결과를 바깥 쿼리가 사용한다(예: 집계 결과, 고정된 값 목록).
  - 상관 서브쿼리: 바깥 쿼리의 각 행에 대해 내부 쿼리가 평가될 수 있어 성능 비용이 크다.
- 실행 계획(Execution Plan)을 읽을 때는 다음을 확인한다:
  - full table scan 여부, index seek/scan 구분
  - 사용된 조인 방식(Nested/Hash/Merge)
  - 조인 순서와 조인 피연산자의 크기
  - 예상 행 수(estimated)와 실제 행 수(actual)의 차이 — 큰 차이는 통계 갱신 필요성 신호
  - 정렬, 해시 스필(임시 디스크 사용) 등으로 인한 추가 비용

## 쉽게 이해하기

- JOIN은 두 표를 공통 열 기준으로 붙이는 작업이다. 예: 고객표(customers)와 주문표(orders)를 customer_id로 연결.
- 서브쿼리는 쿼리 안에 들어 있는 작은 쿼리다. 먼저 구한 결과를 바깥 쿼리 조건으로 사용한다(예: 특정 조건을 만족하는 고객 목록을 먼저 구한 뒤, 그 고객들만 조회).
- 감각적으로는 JOIN은 표를 옆으로 붙이는 느낌, 서브쿼리는 중간 결과를 이용해 필터링하는 느낌으로 이해하면 편하다.

## 예제와 주의점

- INNER JOIN 예제

```sql
SELECT c.customer_id, c.name, o.order_id, o.amount
FROM customers c
INNER JOIN orders o
  ON c.customer_id = o.customer_id
WHERE o.order_date >= '2024-01-01';
```
- 비상관 서브쿼리 예제(한 번만 실행)

```sql
SELECT customer_id, name
FROM customers
WHERE customer_id IN (
  SELECT customer_id FROM orders WHERE amount > 100
);
```

- 상관 서브쿼리 예제(바깥 행마다 실행될 수 있음)

```sql
SELECT c.customer_id, c.name
FROM customers c
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
    AND o.amount > 100
);
```

성능 및 의미상의 차이 요약:
- IN vs EXISTS: 일부 DBMS에서 결과가 같아도 실행 계획이 다를 수 있다. NULL 값이 포함된 컬럼을 IN에 사용하면 의도치 않은 결과가 나올 수 있으므로 주의한다.
- JOIN으로 재작성하면 중복 행이 생길 수 있음(일대다 관계). 중복을 제거하려면 DISTINCT 또는 그룹화가 필요하다.
- 상관 서브쿼리는 바깥 행 수가 많으면 큰 비용을 초래하므로 조인으로 재작성하거나 인덱스를 추가해 최적화할 수 있다.

## 시험 포인트(단답/서술 대비)

- INNER JOIN과 LEFT OUTER JOIN의 차이를 간단히 설명하라.
- 상관 서브쿼리와 비상관 서브쿼리의 특징과 성능 차이를 설명하라.
- Nested Loop, Hash Join, Sort-Merge의 사용 조건과 장단점을 쓰시오.
- NOT IN과 NOT EXISTS의 차이점(특히 NULL 처리)을 설명하라.
- 실행 계획에서 index seek/scan, estimated vs actual rows를 보고 문제점을 진단하는 절차를 쓰시오.

## 실무 연결(현업에서 확인할 것)

- 실행계획(Explain Plan)을 항상 확인한다. 특히 큰 테이블 조인의 경우 예상 행 수와 실제 행 수 차이를 보면 통계 문제나 인덱스 설계 문제를 찾을 수 있다.
- 상관 서브쿼리로 인한 반복 실행을 발견하면 JOIN 또는 EXISTS로 재작성해 성능을 개선할 수 있는지 검토한다.
- 인덱스 설계 시 조회 패턴(필터링, 조인 키, 정렬 키)을 고려한다. 조인 컬럼에 적절한 인덱스가 있으면 Nested Loop 성능이 향상된다.
- 집계나 DISTINCT 처리가 필요한지 확인하여 조인 후 불필요한 중복을 제거하라(예: 고객별 총액을 원할 때는 그룹화 사용).
- 대용량 조인 시 메모리 사용과 임시 디스크(스필) 여부를 확인하여 리소스 계획을 한다.

## 실무 체크리스트

- [ ] 실행계획 확인: index seek/scan, join type, estimated vs actual rows
- [ ] 통계(Statistics) 최신화 여부 확인
- [ ] 조인 키에 적절한 인덱스 존재 여부 점검
- [ ] 서브쿼리(특히 상관 서브쿼리) 재작성으로 성능 개선 가능성 검토
- [ ] NULL 관련 논리 오류(NO IN vs EXISTS) 확인

## 흔한 실수와 디버깅 팁

- JOIN으로 재작성하면서 결과 중복을 간과해 잘못된 집계나 개수를 얻는 경우가 많다. 반드시 의도한 행 단위(고유성)를 확인하라.
- NOT IN 사용 시 비교 대상 컬럼에 NULL이 존재하면 결과가 사라질 수 있다. NOT EXISTS로 바꾸어 검증하라.
- 예상 행 수와 실제 행 수가 크게 다르면 통계를 업데이트하거나 힌트를 사용하는 대신 먼저 왜 차이가 나는지(데이터 분포 변화, 오래된 통계) 확인하라.
- 작은 샘플 데이터로는 실행 계획이 다르게 나올 수 있다. 성능 검증은 실제 데이터 분포 또는 충분히 큰 샘플로 수행하라.
