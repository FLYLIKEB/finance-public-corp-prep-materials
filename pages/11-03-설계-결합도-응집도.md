# 11-03. 설계-결합도-응집도

> 학습 목적: 좋은 모듈 설계 기준을 암기한다.
> 관련 기출: [05-13-알고리즘-기출-모음](05-13-알고리즘-기출-모음.md)
> 연결 핵심정리: [04-3-소프트웨어공학-운영체제-컴퓨터구조](04-03-소프트웨어공학-운영체제-컴퓨터구조.md)

## 핵심 개념

- 결합도는 모듈(또는 컴포넌트) 간의 의존(연결) 정도다. 결합도가 높으면 한 모듈 변경이 다른 모듈에 영향을 크게 미친다.
- 응집도는 모듈 내부의 구성요소들이 하나의 목적을 위해 얼마나 밀접하게 관련되어 있는지다. 응집도가 높을수록 모듈의 응집된 책임이 명확하다.
- 좋은 설계는 낮은 결합도와 높은 응집도를 지향한다. 특히 금융공기업 시스템처럼 안정성과 변경 용이성이 중요한 환경에서는 더욱 중요하다.

- 결합도 유형(낮은 순 -> 높은 순, 암기 포인트)
  - 자료 결합(Data coupling): 매개변수(데이터)를 통해 통신. 가장 바람직.
  - 스탬프 결합(Stamp/Structure coupling): 구조체/레코드를 전달.
  - 제어 결합(Control coupling): 제어 정보를 전달(플래그 등).
  - 외부 결합(External coupling): 외부 규약/인터페이스에 의존.
  - 공통 결합(Common coupling): 전역 데이터(또는 공유 자원)에 의존.
  - 내용 결합(Content coupling): 다른 모듈의 내부 구현을 직접 사용. 가장 나쁨.

- 응집도 유형(높은 순 -> 낮은 순, 암기 포인트)
  - 기능적 응집(Functional cohesion): 모듈이 하나의 주요 기능을 수행. 가장 이상적.
  - 순차적 응집(Sequential cohesion): 출력이 다음 부분의 입력으로 사용되는 구성요소.
  - 통신적 응집(Communicational cohesion): 같은 데이터에 작용하는 기능들이 모여 있음.
  - 절차적 응집(Procedural cohesion): 일련의 절차 단계들이 모여 있음.
  - 시간적 응집(Temporal cohesion): 동일한 시점(초기화, 종료)에 실행되는 기능들.
  - 논리적 응집(Logical cohesion): 유사한 기능들을 조건에 따라 수행. 낮음.
  - 우연적 응집(Coincidental cohesion): 관련 없는 기능들이 우연히 모여 있음. 가장 나쁨.

### 서술형 확장 개념

- 좋은 설계는 정보 은닉(encapsulation), 추상화(abstraction), 모듈화(modularization)를 통해 변경의 영향을 국소화한다. 금융 서비스에서 예를 들면 계좌(Account) 모듈의 내부 데이터 구조 변경이 트랜잭션 처리 모듈 전체를 흔들지 않도록 인터페이스를 통해 접근하게 한다.
- SOLID 원칙은 객체지향 설계의 변경 용이성을 높이고 테스트 가능성을 개선한다. 각 원칙의 한줄 요약과 금융 시스템 적용 예시는 다음과 같다.
  - 단일 책임 원칙(SRP): 한 클래스는 하나의 책임만 가져야 한다. (예: 계좌 잔액 관리와 보고서 생성은 분리)
  - 개방-폐쇄 원칙(OCP): 확장에는 열려 있고 변경에는 닫혀 있어야 함. (예: 보상 정책 추가는 기존 코드 변경 없이 플러그형으로 처리)
  - 리스코프 치환 원칙(LSP): 서브타입은 슈퍼타입을 대체할 수 있어야 함. (예: 결제수단 인터페이스를 구현한 모든 클래스가 동일 계약을 지킴)
  - 인터페이스 분리 원칙(ISP): 클라이언트는 자신이 사용하지 않는 인터페이스에 의존하면 안 됨. (예: 리포트 생성 인터페이스와 트랜잭션 처리 인터페이스 분리)
  - 의존성 역전 원칙(DIP): 고수준 모듈은 저수준 모듈에 의존하지 말고, 추상화에 의존해야 함. (예: DB 접근은 인터페이스로 추상화하고 DI로 주입)

- 결합도-응집도 관련 시험 대비 팁
  - 서술형 문제에서는 항상 "결합도는 낮게, 응집도는 높게"를 명시하고, 각 단계(자료-내용, 기능적-우연적)를 순서대로 적어라.
  - 실무 예시(간단한 사례)를 한두 줄로 첨부하면 가산점: 예) "거래 처리 모듈은 트랜잭션 단위 검증/커밋 책임만 갖고, 보고서 생성은 별도 모듈로 분리(응집도↑, 결합도↓)".
  - 디자인 패턴을 언급할 때는 패턴의 의도와 금융 시스템에서의 적용 예시를 함께 쓰면 효과적이다.

- 디자인 패턴 요약(금융공기업 맥락 예시)
  - Singleton: DB 커넥션 풀이나 설정 manager처럼 애플리케이션 전역에 하나만 존재해야 하는 객체에 사용 가능(주의: 테스트/병렬성 고려).
  - Factory: 다양한 계좌(Account) 타입(저축, 당좌, 신탁 등) 객체 생성을 캡슐화.
  - Adapter: 외부 결제사 API 인터페이스를 내부 결제 인터페이스로 변환.
  - Observer: 계좌 잔액 변경 시 알림(모니터링/보고서/감사 로그 업데이트)을 트리거.
  - MVC: 전통적인 웹 UI 분리(모델: 도메인/비즈니스, 뷰: 화면, 컨트롤러: 요청 처리).

| 원칙/패턴 | 핵심 의도 |
| --- | --- |
| 정보은닉 | 내부 구현 변경이 외부에 퍼지지 않게 함 |
| SOLID | 변경에 강한 객체지향 의존관계 구성 |
| Factory | 생성 로직을 캡슐화 |
| Observer | 이벤트 기반 통지 |
| MVC | 관심사 분리 |

## 쉽게 이해하기

- 결합도 비유: 건물의 각 층이 서로 계단(인터페이스)로만 연결되어 있으면(낮은 결합도) 한 층을 고쳐도 다른 층에 미치는 영향이 적다. 계단을 뚫고 벽을 통째로 공유하면(높은 결합도) 한 곳 수정 시 전 층이 흔들린다.
- 응집도 비유: 주방은 요리 재료와 도구가 모두 주방에 모여 있을 때(높은 응집도) 기능이 명확하다. 다양한 성격의 물건(책, 신발, 주방도구)이 한 방에 섞여 있으면(낮은 응집도) 목적이 불명확하다.

- 금융 시스템 예시(간단):
  - 거래 입력 -> 검증 -> 회계 분개 -> 장부 반영의 순차적 응집을 가질 수 있다. 각 단계는 명확히 분리되어 인터페이스로 연결하면 결합도를 낮출 수 있다.
  - 보고서 생성과 실시간 거래 처리는 서로 다른 모듈로 분리(응집도↑, 결합도↓). 보고서는 트랜잭션 로그를 읽는 방식으로 간접 연결(자료 결합)을 사용.

## 실전 암기 체크리스트

- [ ] 결합도 정의와 낮은->높은 순서(자료, 스탬프, 제어, 외부, 공통, 내용) 암기
- [ ] 응집도 정의와 높은->낮은 순서(기능적, 순차적, 통신적, 절차적, 시간적, 논리적, 우연적) 암기
- [ ] SOLID 원칙 각각의 의도와 금융 예시 1개씩 정리
- [ ] 디자인 패턴 4~5개(Factory, Singleton, Adapter, Observer, MVC) 의도와 금융 적용 예시 암기
- [ ] 서술형 모의 답안 2개(결합도/응집도 설명, 설계 개선 방안) 작성 연습
