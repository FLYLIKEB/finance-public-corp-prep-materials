## 오픈뱅킹 구조

오픈뱅킹은 은행별로 분산된 계좌 조회·이체 기능을 표준 API로 제공해 핀테크와 금융기관이 연결되도록 하는 인프라입니다. 사용자는 하나의 서비스에서 여러 금융기관 계좌를 조회하고 이체할 수 있습니다.

핵심 구성요소는 다음과 같이 정리할 수 있습니다.

- **API 제공자**: 계좌 조회, 잔액 조회, 이체 같은 금융 기능을 노출하는 은행·금융기관
- **API 소비자**: 사용자의 동의를 받아 기능을 호출하는 핀테크·플랫폼 사업자
- **인증·인가 서버**: 사용자 인증, 동의 범위 확인, 토큰 발급을 담당하는 구성요소
- **API Gateway**: 인증, 인가, rate limit, 로깅, 라우팅, 장애 격리를 공통 처리하는 진입점
- **모니터링/감사 체계**: 누가 어떤 권한으로 어떤 API를 호출했는지 추적하는 로그 기반 운영 장치

금융권에서는 단순 연결보다 "표준화된 안전한 연결"이 중요합니다. 그래서 오픈뱅킹 구조를 설명할 때는 편의성뿐 아니라 토큰 관리, 호출 한도, 이상 거래 탐지까지 함께 말해야 합니다.

## API 표준

금융 API는 인증, 권한 위임, 호출 한도, 응답 코드, 전문 포맷을 표준화해야 합니다. 표준화가 부족하면 기관별 연동 비용이 커지고 장애 원인 추적이 어려워집니다.

실무에서 특히 자주 보는 표준화 포인트는 아래와 같습니다.

- 인증·인가 방식: OAuth2 authorization code flow, client authentication, 토큰 만료·재발급 정책
- 요청/응답 형식: 필드명, 날짜·금액 형식, 오류 코드 체계, 멱등성 키 사용 규칙
- 운영 계약: 호출량 제한, 타임아웃, 재시도 정책, 장애 공지와 버전 정책
- 보안 요구: TLS/mTLS, 전자서명, 인증서 교체, 접근 로그와 감사 로그 보존

간단한 호출 흐름은 다음처럼 이해하면 됩니다.

```http
GET /authorize?response_type=code&client_id=CLIENT_ID&scope=accounts transfers
POST /token
GET /accounts
Authorization: Bearer ACCESS_TOKEN
```

면접에서는 이 예시를 바탕으로 "사용자 동의 → 토큰 발급 → API 호출 → 로그 추적" 순서로 설명하면 구조 이해를 보여주기 쉽습니다.

## 마이데이터 서비스 구조

마이데이터는 개인이 자신의 금융 데이터를 통제하고, 동의 기반으로 제3자에게 전송하도록 하는 체계입니다. 핵심은 본인 인증, 전송 요구권, 데이터 표준화, 동의 철회, 접근 로그 관리입니다.

구현 관점에서 중요 포인트는 다음과 같습니다.

- **동의 관리**: 어떤 데이터를 어떤 목적으로 얼마나 오래 쓰는지 명확히 기록해야 한다.
- **데이터 표준화**: 기관별로 다른 계좌·카드·대출 데이터를 공통 스키마로 맞춰야 한다.
- **최소 권한**: 필요한 데이터만 요청하고, 목적이 바뀌면 재동의를 받아야 한다.
- **추적 가능성**: 조회·전송·정정 이력이 남아야 감사와 민원 대응이 가능하다.
- **보안 통제**: 전송 구간 암호화, 저장 구간 암호화, 접근통제, 이상 접근 탐지가 기본이다.

데이터를 많이 모으는 서비스처럼 보이지만, 실제 핵심은 많이 모으는 것이 아니라 **적법하게, 설명 가능하게, 철회 가능하게** 다루는 것입니다.

## 면접 포인트

오픈뱅킹은 편의성, 마이데이터는 정보 주권, 금융보안은 신뢰를 담당합니다. 세 가지를 함께 설명하면 금융IT 도메인 이해도가 높게 보입니다.

답변을 구성할 때는 아래 틀을 쓰면 안정적입니다.

1. 오픈뱅킹: 표준 API로 금융 기능을 외부에 개방하는 구조
2. 마이데이터: 정보주체 동의 기반으로 데이터를 통합 활용하는 체계
3. 보안/운영: 인증·인가, 로그, 이상 탐지, 동의 철회, 장애 대응이 필수
4. 실무 연결: API Gateway, 토큰 수명주기, 제휴사 온보딩, 샌드박스 운영

예상 질문 예시는 다음과 같습니다.

- 오픈뱅킹과 마이데이터의 차이는 무엇인가?
- OAuth2가 금융 API에서 중요한 이유는 무엇인가?
- 동의 철회가 발생하면 어떤 시스템 처리가 필요한가?
- 대량 호출이나 이상 호출을 어떻게 탐지하고 차단할 것인가?

## 핵심 개념

- 오픈뱅킹은 표준 API로 계좌조회·이체 등 금융 기능을 외부 서비스가 사용할 수 있게 하는 구조다. API Gateway는 인증, 인가, rate limit, 로깅, 라우팅을 담당한다.
- OAuth2는 사용자의 비밀번호를 제3자에게 직접 주지 않고 access token으로 권한을 위임하는 방식이다. 금융권에서는 동의 범위, 토큰 만료, 재동의, 이상 호출 탐지가 중요하다.
- 마이데이터는 정보주체의 전송요구권과 동의를 기반으로 흩어진 금융 데이터를 통합 활용하는 체계다. 표준 API, 최소권한, 목적 제한, 암호화, 접근기록 관리가 함께 필요하다.
- 운영 단계에서는 제휴사 등록, 인증서 교체, 장애 공지, 로그 보존 같은 절차까지 관리해야 서비스가 지속 가능하다.

### 실무 체크리스트

- [ ] API 스펙과 오류 코드 체계를 문서화했다.
- [ ] OAuth2 토큰 수명주기와 재동의 정책을 정의했다.
- [ ] 동의 범위·보유 기간·철회 절차를 시스템에서 추적할 수 있다.
- [ ] 호출량 제한, 이상 탐지, 감사 로그 보존 정책을 운영에 반영했다.

## 약어 풀이

- API: Application Programming Interface, 응용 프로그램 인터페이스
- OAuth2: Open Authorization 2.0, 권한 위임 프로토콜
- JWT: JSON Web Token, 토큰 기반 정보 표현 형식
- mTLS: mutual Transport Layer Security, 상호 인증 TLS
