# 07-05. 인덱스와 동시성

> 학습 목적: 인덱스 장단점과 동시성 제어를 정리한다.
> 관련 기출: [05-10-데이터베이스-기출-모음](05-10-데이터베이스-기출-모음.md)
> 연결 핵심정리: [04-5-자료구조-알고리즘-DB-금융IT](04-05-자료구조-알고리즘-DB-금융IT.md)

## 핵심 개념

- 인덱스는 검색 속도를 높이지만 쓰기 비용을 늘린다. (추가 저장공간, INSERT/UPDATE/DELETE 시 인덱스 유지 비용)
- 동시성 제어는 여러 트랜잭션의 일관성을 지킨다. (원자성·일관성·격리성·지속성 중 격리성 관련)
- 로킹(locking)과 타임스탬프(timestamp) 기법을 구분한다. MVCC는 버전 관리를 통한 읽기/쓰기 분리를 제공한다.


### 서술형 확장 개념

- **B+Tree 인덱스**
  - 특징: 균형 트리 구조로 모든 실제 레코드 포인터는 리프 노드에 존재. 리프 노드들이 순차 연결되어 range scan(범위 검색)과 정렬이 빠르다.
  - 장점(시험에 쓸 한 줄): "B+Tree는 범위 검색과 ORDER BY, BETWEEN에 유리하며 리프 연결로 순차 접근을 효율화한다."
  - 예시: 복합 키 인덱스에서 앞쪽 컬럼을 기준으로 범위 검색을 할 때 효과적.

- **Hash 인덱스**
  - 특징: 키를 해시값으로 변환해 직접 버킷에서 탐색하므로 동등 조건(=)에 매우 빠르다. 범위 검색이나 정렬에는 적합하지 않음.
  - 장점(시험에 쓸 한 줄): "Hash 인덱스는 동등 비교에 최적화돼 있지만 BETWEEN/ORDER BY에는 부적합하다."
  - 예시: WHERE user_id = 1234 같은 질의에 적합.

- **클러스터드 인덱스(Clustered Index)**
  - 특징: 인덱스 키의 물리적 저장 순서가 데이터 저장 순서와 일치한다. 한 테이블에 보통 하나만 존재.
  - 장점: 범위 검색이 빠르나, 삽입 시 데이터 재배치 비용이 높을 수 있다.
  - 주의: DBMS별로 구현과 명명법이 다르다(SQL Server는 CLUSTERED INDEX, MySQL InnoDB는 PK가 클러스터드).

- **논클러스터드 인덱스(Non-clustered Index)**
  - 특징: 별도의 구조에서 키와 데이터(또는 레코드 포인터)를 관리한다. 클러스터드가 없는 테이블에서 많이 사용.

- **2PL (Two-Phase Locking)**
  - 동작: 트랜잭션은 먼저 lock을 획득하는 growing phase를 거친 뒤, lock을 해제하는 shrinking phase를 거친다. 이로써 conflict-serializable을 보장한다.
  - strict 2PL: 모든 exclusive lock을 트랜잭션이 종료(commit/abort)될 때까지 해제하지 않아 cascading abort를 방지한다.
  - 시험답안 한 줄: "2PL은 획득과 해제의 두 단계로 진행되어 직렬화 가능성을 보장하며, strict 2PL은 더 강한 회복성(rollback 안전)을 제공한다."

- **타임스탬프 순서(Timestamp Ordering)**
  - 동작: 각 트랜잭션에 논리적 시작 시각(타임스탬프)을 부여하고, 읽기/쓰기 요청의 순서를 이 타임스탬프에 따라 허용하거나 거부한다.
  - 장단점: deadlock은 발생시키지 않지만, 충돌 시 트랜잭션이 롤백될 수 있다.

- **MVCC (Multi-Version Concurrency Control)**
  - 동작: 데이터를 여러 버전으로 유지하여 읽기는 과거의 안정된 버전을 참조하게 하고, 쓰기는 새로운 버전을 생성한다.
  - 장점: 읽기와 쓰기의 충돌이 줄어들어 높은 동시 읽기 성능(읽기 비차단)을 제공한다. 예: PostgreSQL, Oracle, InnoDB의 일부 동작.
  - 시험답안 한 줄: "MVCC는 버전 기반으로 읽기 일관성을 제공하여 읽기 작업의 잠금 경쟁을 줄인다."

| Join 알고리즘 | 적합한 상황 | 핵심 비용 요인 |
| --- | --- | --- |
| Nested Loop Join | 한쪽 입력이 작거나 인덱스가 있음 | 반복 탐색 횟수 |
| Hash Join | 동등 조인, 메모리 충분 | 해시 테이블 구축/탐색 |
| Sort-Merge Join | 양쪽이 정렬되어 있거나 범위 처리 | 정렬 비용 |

## 쉽게 이해하기

- 인덱스는 책 뒤의 찾아보기와 같다. 원하는 내용을 빨리 찾게 해 주지만, 책 내용이 바뀔 때 찾아보기도 함께 고쳐야 한다. (읽기는 빨라지고, 쓰기는 느려짐)
- 동시성은 여러 사용자가 동시에 DB를 써도 결과가 꼬이지 않게 하는 문제다. 예: 두 사용자가 같은 계좌 잔액을 동시에 갱신하면 잔액이 틀려질 수 있다.
- 잠금은 한 사람이 수정하는 동안 다른 사람이 건드리지 못하게 하는 표시라고 보면 된다. (공유 잠금: 읽기 허용, 배타 잠금: 쓰기 전용)

- 문제: B+Tree와 Hash 인덱스의 차이를 한 문장으로 설명하시오.
  - 모범 답안: "B+Tree는 범위 검색과 정렬에 유리한 균형 트리 구조이고, Hash는 동등 조건 검색에 특화되어 범위/정렬에는 부적합하다."
- 문제: strict 2PL의 장점을 서술하시오.
  - 모범 답안: "strict 2PL은 배타적 잠금을 트랜잭션 종료까지 유지해 cascading abort를 방지하고 회복성을 높인다."
- 문제: MVCC의 핵심 이점은 무엇인가?
  - 모범 답안: "읽기 작업이 잠금에 의해 차단되지 않고 과거 버전을 참조함으로써 높은 동시성의 읽기 성능을 제공한다."

## 비교표(요약: 인덱스/동시성 기법)

| 항목 | 장점 | 단점 | 대표 사용처/주의사항 |
| --- | --- | --- | --- |
| B+Tree 인덱스 | 범위 검색·정렬 효율적 | 다중 인덱스 유지 비용, 업데이트 오버헤드 | ORDER BY, BETWEEN 등에 적합 |
| Hash 인덱스 | 동등 검색 매우 빠름 | 범위·정렬 불가 | 키가 고유하고 동등 조회가 많은 경우 유리 |
| 클러스터드 인덱스 | 범위 검색 빠름, 데이터 로컬리티 | 테이블당 1개, 삽입/재배치 비용 | PK로 자주 범위 조회할 때 사용 |
| 2PL | 직렬성 보장 가능 | 데드락 발생 가능 | 트랜잭션 격리 필요 시스템에서 사용 |
| Timestamp | 데드락 없음 | 충돌 시 트랜잭션 롤백 | 읽기/쓰기 순서 규정 필요 |
| MVCC | 읽기 비차단, 높은 읽기 동시성 | 버전 관리 오버헤드(디스크/GC) | 읽기 많은 OLTP에 유리 |

## 약어 풀이

- DB: Database, 데이터베이스
- B+Tree: B Plus Tree (균형 트리의 한 형태)
- MVCC: Multi-Version Concurrency Control (다중 버전 동시성 제어)
- 2PL: Two-Phase Locking (두 단계 잠금)
