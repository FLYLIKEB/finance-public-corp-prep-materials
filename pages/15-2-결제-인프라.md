## BOK-Wire+

BOK-Wire+는 한국은행이 운영하는 거액결제 시스템입니다. 금융기관 간 대규모 자금 이체를 실시간 총액결제(RTGS) 방식으로 처리해 시스템 리스크를 줄입니다.

거액결제 시스템에서는 한 건의 실패가 연쇄 유동성 문제로 번질 수 있으므로, 처리 속도보다 **확정성·가용성·무결성**이 더 중요합니다. 면접에서는 "왜 RTGS가 필요한가"를 설명할 때 결제 최종성과 시스템 리스크 축소를 함께 말하면 좋습니다.

- 실시간 처리: 거래를 개별 건으로 즉시 결제해 결제 지연 리스크를 줄인다.
- 총액 결제: 거래별로 전액 결제하므로 상계 이전 단계의 신용위험이 작다.
- 운영 요구: 이중화, 망 분리, 장애 복구 시나리오, 추적 가능한 로그가 필수다.

## 소액결제와 FPS

소액결제 인프라는 국민의 일상 거래를 처리합니다. 실시간 이체와 간편결제 확산으로 빠른 처리와 장애 복구, 중복 거래 방지가 중요해졌습니다.

소액결제에서는 대량 동시 요청을 버티는 처리량과 사용자 체감 속도가 중요합니다. 동시에 실패한 요청의 재시도, 네트워크 끊김, 중복 클릭 같은 현실적인 문제가 자주 발생하므로 UX와 백엔드 설계를 함께 봐야 합니다.

- 처리량 관리: 급여일·점심시간 같은 피크 구간에도 응답시간 SLA를 지켜야 한다.
- 중복 방지: 동일 결제가 두 번 승인되지 않도록 멱등성과 상태 관리가 필요하다.
- 장애 복구: 일시 실패 후 재시도해도 정산 결과가 어긋나지 않아야 한다.

## SWIFT

SWIFT는 국제 금융기관 간 메시징 네트워크입니다. 실제 자금 이동 자체보다 표준화된 지급 지시와 메시지 교환 기능이 핵심입니다.

즉, SWIFT는 "돈이 이동하는 레일"이라기보다 "어떤 돈을 어떻게 이동시킬지 지시를 전달하는 표준 메시지망"에 가깝습니다. 그래서 국제 결제를 설명할 때는 메시징과 실제 결제 계정 이동을 구분해야 합니다.

- 국제 송금 지시, 상태 통지, 정정 메시지 같은 표준 전문을 교환한다.
- 실제 자금 결제는 해당 통화권 결제 시스템이나 코레스 계좌 구조에서 이뤄진다.
- 운영 측면에서는 메시지 포맷, 지연, 재전송, 감사 추적이 중요하다.

## 실시간 결제의 기술 쟁점

- 중복 요청 방지와 멱등성
- 장애 시 재처리와 정산 정합성
- API 인증·암호화·로그 감사
- 피크 트래픽 대응과 모니터링

각 쟁점은 아래처럼 기술 설계와 직접 연결됩니다.

- **멱등성**: 같은 요청이 여러 번 들어와도 결과가 한 번만 반영되도록 요청 식별자와 처리 이력을 관리한다.
- **정산 정합성**: 재처리 시 원장과 대사(reconciliation) 결과가 어긋나지 않도록 단일 기준 원장을 유지한다.
- **보안 통제**: API 인증, 전송 암호화, 중요 이벤트 감사 로그, 키 관리가 함께 있어야 한다.
- **운영 가시성**: TPS, 지연 시간, 오류율, 큐 길이, 재시도율 같은 지표를 실시간으로 봐야 한다.

```http
POST /payments
Idempotency-Key: 3f6b8e4a-1d4b-4f90-9a61-demo
Content-Type: application/json

{
  "amount": 10000,
  "from": "계좌A",
  "to": "계좌B"
}
```

이런 계약을 문서화해 두면 클라이언트 재시도와 서버 중복 처리 방지를 같은 언어로 설명할 수 있습니다.

## 금융공기업 연결

한국은행은 거액결제, 금융결제원은 소액·공동망, 코스콤과 거래소는 자본시장 거래 인프라와 연결됩니다.

기관별 역할을 구분해 이해하면 지원 기관의 업무 범위를 설명하기 쉬워집니다.

- **한국은행**: 거액결제와 최종결제 안정성의 중심 역할
- **금융결제원**: 소액결제, 공동망, 대국민 결제 편의와 연동성 지원
- **코스콤·거래소**: 자본시장 주문·체결·청산·결제와 맞물리는 시장 인프라 지원

금융공기업 IT 직무에서는 각 기관이 단독으로 움직이지 않고 서로 인터페이스와 운영 절차로 연결된다는 점을 이해하는 것이 중요합니다.

## 핵심 개념

- 청산은 지급 지시를 모아 채권·채무를 계산하는 과정이고, 결제는 실제 자금 이전으로 채무를 소멸시키는 과정이다. 최종성(finality)은 결제가 취소되지 않고 확정되는 성질이다.
- RTGS는 건별 총액 실시간 결제로 결제 위험을 줄이지만 유동성 부담이 크다. DNS는 일정 기간 거래를 상계해 순액만 결제하므로 유동성은 절약하지만 결제 시점까지 신용·유동성 위험이 남는다.
- 지급결제 인프라는 고가용성, 장애복구, 이중화, 모니터링, 접근통제, 변경관리까지 포함한 운영 안정성이 핵심이다.

| 방식 | 장점 | 한계 |
| --- | --- | --- |
| RTGS | 결제 위험 낮음, 즉시 최종성 | 유동성 소요 큼 |
| DNS | 유동성 절감 | 결제 전 위험 누적 |

### 운영 체크리스트

- [ ] 결제 API에 멱등성 키와 재시도 정책을 정의했다.
- [ ] 원장, 정산 배치, 대사 절차의 기준 데이터를 명확히 했다.
- [ ] 장애 시 수동 개입 전후 절차와 승인 체계를 문서화했다.
- [ ] 지연, 오류율, 큐 적체, 재처리 건수를 모니터링한다.

## 약어 풀이

- API: Application Programming Interface, 응용 프로그램 인터페이스
- RTGS: Real-Time Gross Settlement, 실시간 총액결제
- DNS: Deferred Net Settlement, 이연차액결제
- FPS: Faster Payment System, 실시간 소액결제 시스템
- SWIFT: Society for Worldwide Interbank Financial Telecommunication, 국제 금융 메시징 네트워크
