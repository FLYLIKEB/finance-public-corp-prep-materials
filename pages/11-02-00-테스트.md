## 핵심 개념

- 테스트는 결함을 발견하고 소프트웨어가 요구사항을 만족하는지 확인하는 품질 보증 활동이다.
- 테스트는 단위 → 통합 → 시스템 → 인수 테스트처럼 범위를 넓혀 가며 수행한다.
- V-모델은 개발 단계와 대응되는 테스트 단계를 연결해 검증·확인의 관계를 보여 준다.

## 테스트의 목적

테스트는 프로그램이 “동작한다”는 사실만 확인하는 활동이 아니다. 숨어 있는 결함을 발견하고, 요구사항 충족 여부를 근거로 품질을 판단하며, 운영 중 장애 가능성을 줄이는 활동이다.

- 결함 발견: 오류, 누락, 경계 조건 문제를 찾는다.
- 품질 평가: 성능, 안정성, 보안성 등 품질 특성을 확인한다.
- 위험 감소: 배포 전 장애 가능성을 낮춘다.
- 의사결정 지원: 출시 가능 여부와 수정 우선순위를 판단한다.

## V-모델

V-모델은 왼쪽의 개발 산출물과 오른쪽의 테스트 단계를 대응시킨 모델이다.

| 개발 단계 | 대응 테스트 | 확인 내용 |
| --- | --- | --- |
| 요구사항 분석 | 인수 테스트 | 사용자 요구사항을 만족하는가 |
| 시스템 설계 | 시스템 테스트 | 전체 시스템이 명세대로 동작하는가 |
| 아키텍처·상세 설계 | 통합 테스트 | 모듈 간 인터페이스가 올바른가 |
| 구현 | 단위 테스트 | 개별 모듈·함수가 올바른가 |

V-모델 문제에서는 “어떤 개발 산출물을 검증하는 테스트인가”를 묻는 경우가 많다.

## 테스트 레벨 개요

| 테스트 레벨 | 범위 | 주요 목적 |
| --- | --- | --- |
| 단위 테스트(Unit Test) | 함수, 클래스, 모듈 | 개별 구성 요소의 논리 오류 발견 |
| 통합 테스트(Integration Test) | 모듈 간 연결 | 인터페이스, 데이터 흐름, 호출 관계 검증 |
| 시스템 테스트(System Test) | 전체 시스템 | 기능·비기능 요구사항 충족 확인 |
| 인수 테스트(Acceptance Test) | 사용자 관점 | 고객·사용자 요구 충족 및 인수 여부 판단 |

## 테스트 기법 개요

- 블랙박스 테스트: 내부 구조를 보지 않고 입력과 출력, 기능 명세를 기준으로 테스트한다.
- 화이트박스 테스트: 내부 코드 구조, 제어 흐름, 조건과 경로를 기준으로 테스트한다.
- 정적 테스트: 실행하지 않고 문서, 코드, 설계를 리뷰·분석한다.
- 동적 테스트: 소프트웨어를 실행해 결과를 관찰한다.

## 빈출 포인트

- V-모델의 개발 단계와 테스트 단계 대응 관계를 암기한다.
- 테스트 레벨은 범위가 단위에서 전체 시스템과 사용자 관점으로 확대된다.
- 블랙박스는 명세 기반, 화이트박스는 구조 기반이라고 구분한다.
- 테스트는 결함이 없음을 증명하는 활동이 아니라 결함을 발견하는 활동이다.

## 오답 포인트

- 시스템 테스트와 인수 테스트를 혼동하지 않는다. 시스템 테스트는 전체 시스템이 명세를 만족하는지, 인수 테스트는 사용자 요구와 인수 기준을 만족하는지 확인한다.
- 통합 테스트는 모듈 내부 로직보다 모듈 사이의 인터페이스 오류를 찾는 데 초점이 있다.
- 테스트를 많이 해도 결함이 전혀 없다는 것을 증명할 수는 없다.

## 빠른 점검

- V-모델에서 요구사항 분석에 대응하는 테스트는 무엇인가?
- 단위, 통합, 시스템, 인수 테스트의 범위를 순서대로 설명할 수 있는가?
- 블랙박스와 화이트박스의 기준 차이를 말할 수 있는가?
