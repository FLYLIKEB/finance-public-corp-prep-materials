## 핵심 개념

- 테스트는 단순히 프로그램이 "동작하는지"만 확인하는 활동이 아니다. 결함을 발견하고, 요구사항 만족 여부를 검증하며, 운영 리스크를 줄이고, 의사결정을 지원하는 품질 보증 활동이다.
- 일반적으로 테스트는 범위와 관점에 따라 단위(Unit) → 통합(Integration) → 시스템(System) → 인수(Acceptance) 테스트처럼 단계적으로 수행된다.
- V-모델은 개발 산출물(왼쪽)과 대응되는 테스트 단계(오른쪽)를 짝지어 각 산출물이 어떻게 검증되는지를 시각화한 모델로, 각 개발 단계의 산출물이 어떤 테스트에 의해 확인되는지를 이해하는 데 유용하다.
- 테스트 기법은 테스트 대상의 내부 구조를 보는지(화이트박스) 또는 보지 않는지(블랙박스)에 따라 분류되며, 실행 없이 문서·코드를 검토하는 정적 테스트와 실제 실행을 통해 검증하는 동적 테스트로 나뉜다.

## 테스트의 목적 (구체화)

테스트를 수행할 때 기대하는 산출물과 목적은 다음과 같다.

- 결함 발견: 입력 경계값, 예외 경로, 동시성 문제 등 코드·설계 상의 결함을 찾아냄.
- 품질 평가: 성능(응답시간, 처리량), 안정성(장기 동작), 보안(취약점), 사용성(사용자 경험) 등 비기능 요구사항 확인.
- 위험 감소: 운영환경과 유사한 환경에서 문제를 사전에 발견해 배포 위험을 낮춤.
- 의사결정 지원: 테스트 결과(결함 수, 심각도, 재현성 등)를 바탕으로 릴리스 여부와 우선순위를 결정.

성공 판단 기준(예시): 통과 테스트 케이스 비율, 잔존 결함의 심각도, 목표 성능 지표 충족 여부.

## V-모델

V-모델은 개발 단계와 대응되는 테스트 단계를 명확히 한다. 각 개발 산출물은 오른쪽 대응되는 테스트 단계에서 검증된다.

| 개발 단계 | 대응 테스트 | 확인 내용 |
| --- | --- | --- |
| 요구사항 분석 | 인수 테스트 | 사용자 요구사항을 만족하는가 |
| 시스템 설계 | 시스템 테스트 | 전체 시스템이 명세대로 동작하는가 |
| 아키텍처·상세 설계 | 통합 테스트 | 모듈 간 인터페이스가 올바른가 |
| 구현 | 단위 테스트 | 개별 모듈·함수가 올바른가 |

시험·실무 포인트:
- "어떤 개발 산출물을 검증하는 테스트인가" 유형의 문제가 자주 출제된다. 예: 설계 산출물은 통합 테스트/시스템 테스트에서 어떻게 검증되는가?
- V-모델은 각 개발 산출물과 테스트 산출물(테스트 케이스, 검증 기준)을 매핑하는 데 유용하며, 테스트 활동을 앞당겨 설계 품질을 개선할 수 있다.

## 테스트 레벨 개요

| 테스트 레벨 | 범위 | 주요 목적 |
| --- | --- | --- |
| 단위 테스트(Unit Test) | 함수, 클래스, 모듈 | 개별 구성 요소의 논리 오류 발견 |
| 통합 테스트(Integration Test) | 모듈 간 연결 | 인터페이스, 데이터 흐름, 호출 관계 검증 |
| 시스템 테스트(System Test) | 전체 시스템 | 기능·비기능 요구사항 충족 확인 |
| 인수 테스트(Acceptance Test) | 사용자 관점 | 고객·사용자 요구 충족 및 인수 여부 판단 |

각 레벨별 실무 예시:
- 단위 테스트: 경계값, 예외 처리, 반환값 검증 — 빠르게 실행되어 개발 중 자주 실행.
- 통합 테스트: 데이터베이스 연동, 외부 API 호출, 메시지 큐와의 상호작용 검증.
- 시스템 테스트: 전체 서비스 시나리오(로그인 → 주문 → 결제 → 알림) 검증, 성능·보안 테스트 포함.
- 인수 테스트: 고객의 요구를 반영한 엔드투엔드 검증, 수용기준(Acceptance Criteria) 충족 여부 확인.

## 테스트 기법 개요 (구체화 및 예시)

- 블랙박스 테스트
  - 정의: 내부 구조를 고려하지 않고 요구사항·명세서 기반으로 입력과 출력의 정상/비정상 케이스를 검증.
  - 기법 예: 동치분할(Equivalence Partitioning), 경계값 분석(Boundary Value Analysis), 결정 테이블(Decision Table), 상태 전이(State Transition).
  - 실무 팁: 명세가 불명확하면 테스트 케이스 설계 이전에 요구사항 명확화 작업 필요.

- 화이트박스 테스트
  - 정의: 내부 코드 구조(제어 흐름, 조건, 루프, 경로)를 기준으로 테스트 케이스를 설계.
  - 기법 예: 문장/분기/조건/경로 커버리지 기준, 루프 테스트.
  - 실무 팁: 복잡한 분기·루프가 있는 함수는 화이트박스 테스트로 충분한 경로를 커버해야 함.

- 정적 테스트
  - 정의: 코드를 실행하지 않고 코드 리뷰, 정적 분석 도구, 설계·요구사항 검토로 결함을 찾음.
  - 장점: 실행 전 결함을 조기에 발견 가능, 비용 절감 효과.

- 동적 테스트
  - 정의: 소프트웨어를 실제로 실행해 입력에 대한 출력과 동작을 관찰함.
  - 범주: 단위·통합·시스템·인수 테스트 등 모든 레벨의 실행 기반 검증.

## 시험 포인트 (요약)

- 용어 정의: 단위·통합·시스템·인수 테스트의 목적과 범위를 정확히 구분할 수 있어야 한다.
- V-모델 매핑: 각 개발 산출물이 어떤 테스트 단계에서 검증되는지 답할 수 있어야 한다.
- 테스트 기법 구분: 블랙박스 vs 화이트박스, 정적 vs 동적의 차이를 설명하고 예를 들 수 있어야 한다.
- 테스트 설계: 동치분할과 경계값 분석의 차이, 상태 전이 테스트의 적용 상황 등을 예시로 설명할 수 있어야 한다.

예상 문제 유형:
- "다음 개발 산출물은 어느 테스트 레벨에서 검증되는가?"
- "블랙박스 테스트 기법 2가지를 쓰고 각 기법의 목적을 설명하라."
- "정적 테스트의 장점과 한계를 서술하라."

## 실무 연결 (구체적 적용 포인트)

- 자동화: 단위 테스트와 통합 테스트 일부는 자동화해 CI/CD 파이프라인에 통합하면 회귀 방지와 빠른 피드백 제공에 유리하다.
- 테스트 환경: 운영과 유사한 테스트 환경(데이터, 네트워크, 설정)을 구성해 환경 차이로 인한 문제를 줄인다.
- 목(Mock)과 스텁: 외부 의존성(서드파티 API, 외부 DB 등)은 목/스텁으로 격리해 테스트의 신뢰성과 반복성을 확보한다.
- 테스트 데이터 관리: 재현 가능한 테스트를 위해 고정된 테스트 데이터 혹은 데이터 생성 스크립트를 관리한다.
- 비기능 테스트: 성능, 부하, 보안 테스트는 시스템 테스트 단계에서 별도 계획과 기준을 두고 수행한다.
- 결함 관리: 발견된 결함은 우선순위(Severity, Priority)를 부여해 릴리스 여부와 수정 순위를 결정한다.
- 메트릭: 테스트 커버리지, 결함 밀도(Defect Density), 테스트 통과율 등 지표로 품질과 리스크를 모니터링한다.

  - [ ] 요구사항/명세서 기반의 테스트 케이스가 작성되어 있는가?
  - [ ] 테스트 환경(데이터, 구성, 접근 권한)이 준비되어 있는가?
  - [ ] 테스트 수행 기준(통과/실패 기준, 우선순위)이 정의되어 있는가?
  - [ ] 결함 기록 및 추적 체계가 마련되어 있는가?

- 단위 테스트 작성 체크리스트
  - [ ] 한 테스트는 한 가지 동작(behavior)만 검증하는가?
  - [ ] 경계값과 예외 케이스를 포함하고 있는가?
  - [ ] 외부 의존성은 격리(목/스텁)되어 있는가?
  - [ ] 테스트가 빠르고 반복 가능하게 작성되었는가?
  - [ ] 테스트 이름이 의도와 기대 결과를 명확히 설명하는가?

## 예시 코드 (단순화된 단위 테스트 패턴)

```python
# Arrange: 초기 상태/데이터 준비
input_value = 10
expected = 20

# Act: 함수 호출
result = multiply_by_two(input_value)

# Assert: 결과 확인
assert result == expected
```

> 위 예시는 단위 테스트의 Arrange-Act-Assert(준비-실행-검증) 패턴을 보여 준다. 단위 테스트는 빠르고 독립적으로 실행되어야 하며, 복잡한 외부 의존성은 목으로 대체한다.
